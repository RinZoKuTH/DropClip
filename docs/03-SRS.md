# บทที่ 1 บทนำ (Introduction)

## 1.1 ความเป็นมา เหตุผล และแรงจูงใจ

### 1.1.1 ความเป็นมา (Background)
ในยุคปัจจุบัน ผู้ใช้งานอุปกรณ์คอมพิวเตอร์และอุปกรณ์พกพาส่วนใหญ่ไม่ได้จำกัดตนเองอยู่กับระบบนิเวศของผู้ผลิตรายเดียว จากสถิติพบพฤติกรรมการใช้งานอุปกรณ์แบบผสมผสานข้ามค่าย (Cross-Platform Household) เป็นสัดส่วนที่สูงมาก เช่น การใช้งาน iPhone ควบคู่กับ Windows PC หรือการใช้สมาร์ตโฟน Android ควบคู่กับ MacBook 

แม้ผู้ผลิตระบบปฏิบัติการแต่ละค่ายจะพัฒนากลไกอำนวยความสะดวกในการทำงานต่อเนื่องระหว่างอุปกรณ์ (Device Continuity) เช่น Apple Universal Clipboard / AirDrop หรือ Microsoft Phone Link แต่ระบบเหล่านี้ล้วนถูกออกแบบภายใต้สถาปัตยกรรมแบบปิด (Walled Garden) ที่ผูกติดกับระบบนิเวศของตนเองเท่านั้น ส่งผลให้อุปกรณ์ต่างค่ายไม่สามารถเชื่อมต่อกันได้โดยตรง

### 1.1.2 ปัญหาที่พบ (Problem Statement)
จากการศึกษาสภาพการใช้งานจริง พบปัญหาสำคัญ 3 ประการ:
1. **การแตกส่วนของระบบนิเวศ (Ecosystem Fragmentation):** ไม่มีช่องทางมาตรฐานที่เปิดให้อุปกรณ์ต่างระบบปฏิบัติการ (macOS, Windows, iOS, Android) สื่อสารกันโดยตรงในระดับระบบปฏิบัติการ
2. **พฤติกรรมการแก้ปัญหาชั่วคราวที่สร้างต้นทุนแฝงสูง (Workaround Friction):** ผู้ใช้แก้ปัญหาด้วยการส่งข้อความหรือไฟล์หาตัวเองผ่านแอปพลิเคชันแชต (เช่น LINE Keep, Telegram) หรือบริการ Cloud Storage ซึ่งก่อให้เกิดข้อจำกัด:
   - *ขั้นตอนซ้ำซ้อน:* ต้องทำ 5–6 ขั้นตอน (Copy → สลับแอป → วาง → ส่ง → สลับอุปกรณ์ → ดาวน์โหลด)
   - *คอขวดด้านแบนด์วิดท์:* ข้อมูลต้องวิ่งออกอินเทอร์เน็ตภายนอก ทำให้การส่งไฟล์ขนาดใหญ่ทำได้ช้า แม้อุปกรณ์วางอยู่ติดกัน
   - *การลดทอนคุณภาพข้อมูล:* แอปพลิเคชันแชตส่วนใหญ่ทำการ Re-encode และบีบอัดรูปภาพ/วิดีโอจนเสียคุณภาพต้นฉบับ
   - *ความเสี่ยงด้านความปลอดภัยและความเป็นส่วนตัว:* ข้อมูลสำคัญ เช่น ข้อความ รหัสผ่าน หรือไฟล์ส่วนบุคคล ถูกนำไปฝากไว้บนเซิร์ฟเวอร์ของบุคคลที่สาม (Third-Party Cloud)
3. **ช่องว่างของเครื่องมือในปัจจุบัน (Current Tool Limitations):** ซอฟต์แวร์ Open Source ที่มีอยู่ในตลาด เช่น LocalSend ถูกออกแบบมาเพื่อการรับส่งไฟล์ข้ามอุปกรณ์ทั่วไป (Any-to-Any Transfer) จึงบังคับให้ต้องเปิดหน้าต่างโปรแกรมและกดยืนยันรับไฟล์ทุกครั้ง ขาดระบบเฝ้าติดตามคลิปบอร์ดแบบอัตโนมัติ (Passive Clipboard Synchronization) และระบบส่วนใหญ่ยังไม่รองรับการแปลงโครงสร้างข้อมูลภาพในคลิปบอร์ดข้ามระบบปฏิบัติการ

### 1.1.3 แรงจูงใจในการพัฒนา (Motivation)
ทีมพัฒนาจึงต้องการพัฒนา **DropClip** ขึ้นมาเพื่อปิดช่องว่างดังกล่าว โดยมุ่งเน้นการมอบประสบการณ์ Clipboard Continuity ในระดับ Native บนคอมพิวเตอร์ (macOS ↔ Windows) และขยายการทำงานไปยังอุปกรณ์พกพา (iOS / Android) บนเครือข่ายท้องถิ่นโดยตรงแบบ Peer-to-Peer 100% โดยไม่ต้องพึ่งพาเซิร์ฟเวอร์กลาง และยึดหลักการทำงานที่ปลอดภัยและซื่อสัตย์ต่อข้อจำกัดของระบบปฏิบัติการ (Platform-Constrained Honesty)

## 1.2 วัตถุประสงค์ (Objectives)

1. เพื่อพัฒนาระบบถ่ายโอนไฟล์และซิงก์คลิปบอร์ดข้ามแพลตฟอร์มแบบ Peer-to-Peer (P2P) บนเครือข่ายท้องถิ่น (LAN/Wi-Fi) ที่รองรับ 4 ระบบปฏิบัติการหลัก (macOS, Windows, iOS, Android) โดยปราศจากเซิร์ฟเวอร์กลาง (Serverless / Cloudless)
2. เพื่อพัฒนาระบบซิงก์คลิปบอร์ดสองทางแบบอัตโนมัติ (Passive Clipboard Synchronization) ระหว่างระบบปฏิบัติการ Desktop ที่มีความหน่วงต่ำ (Latency p95 < 1,000 ms) พร้อมระบบป้องกันการวนซ้ำของข้อมูล (Loop Prevention)
3. เพื่อพัฒนาระบบถ่ายโอนไฟล์ความเร็วสูงแบบ Streaming ที่สามารถใช้แบนด์วิดท์ฮาร์ดแวร์เครือข่ายท้องถิ่นได้อย่างมีประสิทธิภาพ (Throughput ≥ 60% ของ iperf3 baseline) โดยใช้หน่วยความจำคงที่ (Fixed Memory Allocation < 100 MB) ไม่จำกัดขนาดไฟล์
4. เพื่อพัฒนากลไกแปลงรูปแบบภาพในคลิปบอร์ดข้ามระบบปฏิบัติการ (Cross-OS Image Normalizer) ที่คงคุณภาพและความถูกต้องของภาพต้นฉบับ (SSIM ≥ 0.99)
5. เพื่อออกแบบและพัฒนากลไกความปลอดภัยและความเป็นส่วนตัวในระดับ End-to-End โดยใช้อัตลักษณ์ประจำอุปกรณ์ (Per-Device Identity ECDSA P-256 / secp256r1 ตาม ADR-006) ระบบเข้ารหัส TLS 1.3 และกลไกคัดกรองข้อมูลอ่อนไหว (Sensitive Content Filtering) ออกจากระบบอัตโนมัติ

## 1.3 ขอบเขตของงาน (Scope of Work)

### 1.3.1 สิ่งที่ระบบทำได้ (In Scope)
* **แพลตฟอร์มที่รองรับ:**
  - macOS: เวอร์ชัน 12.0 (Monterey) ขึ้นไป จนถึง macOS เวอร์ชันล่าสุด ณ วันที่เปิดตัว (macOS 15 Sequoia) (รองรับสถาปัตยกรรม Apple Silicon และ Intel)
  - Windows: Windows 10 (Build 19041) หรือ Windows 11 ขึ้นไป จนถึงเวอร์ชันล่าสุด ณ วันที่เปิดตัว (รองรับสถาปัตยกรรม x64 และ ARM64)
  - iOS: เวอร์ชัน 15.0 ขึ้นไป จนถึง iOS เวอร์ชันล่าสุด ณ วันที่เปิดตัว (iOS 18) (รองรับ iPhone และ iPad)
  - Android: เวอร์ชัน 10 (API Level 29) ขึ้นไป จนถึง Android เวอร์ชันล่าสุด ณ วันที่เปิดตัว (Android 15) (สถาปัตยกรรม ARM64)
* **ชนิดข้อมูลคลิปบอร์ดที่รองรับ:** ข้อความธรรมดา (Plain Text), ลิงก์ (URLs), รูปภาพรูปแบบ PNG และ JPEG
* **ความสามารถด้านการถ่ายโอนไฟล์:**
  - ถ่ายโอนไฟล์และโฟลเดอร์แบบ Streaming ผ่าน HTTP/1.1 Chunked over TLS 1.3 ไม่จำกัดขนาด
  - ตรวจสอบความถูกต้องสมบูรณ์ของข้อมูลด้วยอัลกอริทึม SHA-256 Checksum
  - รองรับการถ่ายโอนไฟล์ต่อจากจุดเดิม (Resumable Transfer) เมื่อการเชื่อมต่อขาดหาย
  - รองรับการรับไฟล์อัตโนมัติ (Zero-Click Auto-Accept) สำหรับอุปกรณ์ที่ผ่านการจับคู่แล้ว
* **ความปลอดภัยและการระบุตัวตน:**
  - ค้นหาอุปกรณ์อัตโนมัติผ่าน mDNS/DNS-SD (UDP 5353) ในวง Subnet เดียวกัน
  - จับคู่อุปกรณ์ด้วย QR Code และยืนยันรหัส Short Authentication String (SAS) 6 หลัก
  - เข้ารหัสช่องทางสื่อสารด้วย TLS 1.3 พร้อม Certificate Pinning
  - กรองข้อมูลอ่อนไหวจากโปรแกรมจัดการรหัสผ่าน (Password Managers) และรองรับระบบทำลายข้อมูลชั่วคราว (TTL)

### 1.3.2 ข. ระดับความสามารถตามแพลตฟอร์ม (Platform Capability Tiers)

#### 1.3.2 (ข) ระดับความสามารถของการซิงก์คลิปบอร์ดตามแพลตฟอร์ม (Clipboard Capability Tiers)

เนื่องจากระบบปฏิบัติการแต่ละแพลตฟอร์มมีนโยบายความปลอดภัยและการประมวลผลเบื้องหลัง (Background Execution & Sandbox Policy) ที่แตกต่างกันอย่างมีนัยสำคัญ ระบบจึงกำหนดและประกาศระดับความสามารถในการทำงานของระบบซิงก์คลิปบอร์ดออกเป็น 3 ระดับชั้น (Tiers) อย่างเป็นทางการ ดังนี้:

| ระดับ (Tier) | แพลตฟอร์ม | ทิศทางการทำงาน | รูปแบบการทำงาน (Behavioral Mode) | ข้อจำกัดเชิงสถาปัตยกรรมของ OS (OS Constraints) |
|---|---|---|---|---|
| **Tier 1 — Full Passive** | macOS 12+<br>Windows 10/11 | สองทิศทางแบบสมบูรณ์<br>(Desktop ↔ Desktop) | **อัตโนมัติเต็มรูปแบบ (Zero-Interaction):**<br>ระบบเฝ้าติดตามและดักจับการ Copy จากเบื้องหลัง และเขียนข้อมูลลงคลิปบอร์ดปลายทางทันที | ไม่มีข้อจำกัด — OS อนุญาตให้ Background Daemon เข้าถึง System Clipboard API และทำงานค้างในหน่วยความจำได้อย่างต่อเนื่อง |
| **Tier 2 — Assisted** | Android 10+<br>(API Level 29+) | ทิศทาง Desktop → Android:<br>**อัตโนมัติ (Passive)**<br><br>ทิศทาง Android → Desktop:<br>**กึ่งอัตโนมัติ (Assisted)** | **Desktop → Mobile:** เขียนลงคลิปบอร์ดมือถืออัตโนมัติผ่าน Foreground Service<br>**Mobile → Desktop:** ผู้ใช้สั่งส่งผ่าน Quick Settings Tile, Notification Action Button หรือ Share Sheet (1-Click) | Android 10 ขึ้นไปบังคับใช้นโยบายความเป็นส่วนตัว: **ห้ามแอปพลิเคชันที่ทำงานอยู่เบื้องหลังอ่านข้อมูลจากคลิปบอร์ด** (`getPrimaryClip()`) ยกเว้นแอปพลิเคชัน Input Method (IME) หรือแอปที่อยู่บนหน้าจอด้านหน้า (Foreground Window) เท่านั้น แต่ยังอนุญาตให้เขียนข้อมูลได้ (`setPrimaryClip()`) |
| **Tier 3 — Manual-Assist** | iOS 15+ | สองทิศทางแบบกำหนดคำสั่ง<br>(Interactive/Assisted) | **Desktop → Mobile:** ส่งสัญญาณแจ้งเตือนหรือกดดึงข้อมูลผ่าน App/Widget<br>**Mobile → Desktop:** ส่งผ่าน iOS Share Sheet Extension, Action Button, Interactive Widget หรือ Shortcuts Automation | นโยบายความปลอดภัยและ Sandbox ของ iOS:<br>1. แอปพลิเคชันถูกระงับการทำงาน (Suspended) ภายในไม่กี่วินาทีหลังจากสลับไปเบื้องหลัง<br>2. ไม่อนุญาตให้เปิด Background Socket ค้างไว้เพื่อเฝ้ารับส่งข้อมูลทั่วไป<br>3. iOS 16 ขึ้นไประบบจะแสดงกล่องข้อความขออนุญาตผู้ใช้ (Paste Permission Dialog) ทุกครั้งที่มีการอ่านข้อมูลคลิปบอร์ดข้ามแอป |

> **หมายเหตุข้อกำหนด:** การแบ่งระดับชั้น (Tiers) นี้ **บังคับใช้เฉพาะฟังก์ชันการซิงก์คลิปบอร์ดเท่านั้น** ส่วนฟังก์ชันการถ่ายโอนไฟล์ (File Transfer Engine) สามารถทำงานได้เต็มรูปแบบ (Full Capabilities) ข้ามทั้ง 4 แพลตฟอร์มอย่างเท่าเทียมกัน

### 1.3.3 สิ่งที่ระบบไม่ทำ (Out of Scope)
* **OS-01:** ไม่รองรับการเชื่อมต่อข้ามเครือข่ายอินเทอร์เน็ตสาธารณะ (No Internet Relay / No NAT Traversal / No TURN/STUN) อุปกรณ์ต้องอยู่ในเครือข่ายท้องถิ่นวงเดียวกัน (Same Subnet)
* **OS-02:** ไม่รองรับการทำงานบนเครือข่ายที่เปิดใช้งาน Client Isolation หรือ AP Isolation ในระดับเราเตอร์
* **OS-03:** ไม่รองรับการดักอ่านคลิปบอร์ดเบื้องหลังแบบอัตโนมัติบนระบบปฏิบัติการ iOS และ Android (เนื่องจากติดข้อจำกัดด้าน Sandbox และความเป็นส่วนตัวของ OS)
* **OS-04:** ไม่รองรับข้อมูลคลิปบอร์ดชนิด Rich Text (RTF/HTML) และ Object ไบนารีจำเพาะของโปรแกรมอื่น
* **OS-05:** ไม่รองรับระบบปฏิบัติการ Linux ในเวอร์ชันนี้
* **OS-06:** ไม่มีระบบฐานข้อมูลกลาง บัญชีผู้ใช้ (User Account) หรือการเก็บ Log ผู้ใช้บนระบบคลาวด์
* **OS-07:** ไม่มีความสามารถด้านการควบคุมอุปกรณ์ระยะไกล (Remote Control / Mouse-Keyboard Sharing)

### 1.3.4 ข้อสมมติและความขึ้นต่อกัน (Assumptions and Dependencies)
* **AS-01 (สภาวะเครือข่ายท้องถิ่น):** สันนิษฐานว่าเครือข่าย LAN/Wi-Fi ที่ใช้งานเปิดรับส่งข้อมูลแบบ Multicast (UDP พอร์ต 5353) และไม่มีการเปิดใช้งาน AP Isolation หรือ Client Isolation
* **AS-02 (ความคลาดเคลื่อนของเวลาระบบ):** สันนิษฐานว่านาฬิกาประจำเครื่อง (Physical Wall Clock) ของแต่ละอุปกรณ์มีความคลาดเคลื่อนไม่เกิน $\pm 60$ วินาทีจากเวลามาตรฐาน (เพื่อสอดคล้องกับกลไก HLC และการป้องกัน Replay Attack)
* **AS-03 (ความใกล้ชิดทางกายภาพระหว่างจับคู่):** สันนิษฐานว่าในขั้นตอนการจับคู่อุปกรณ์ (Pairing Flow) ผู้ใช้งานมีอุปกรณ์ทั้งสองเครื่องอยู่ในระยะสายตาและสามารถมองเห็นหน้าจอพร้อมกันเพื่อตรวจสอบความตรงกันของรหัส SAS 6 หลัก
* **DE-01 (ความขึ้นต่อระบบจัดเก็บกุญแจปลอดภัยของ OS):** ระบบพึ่งพา Hardware/OS Secure Key Storage ของแต่ละระบบปฏิบัติการ (macOS/iOS Keychain, Windows CNG/DPAPI, Android Keystore API 29+) สำหรับการเก็บรักษา Private Key อัตลักษณ์อุปกรณ์
* **DE-02 (สิทธิ์การเข้าถึงระบบเครือข่ายและระบบปฏิบัติการ):** ระบบพึ่งพาสิทธิ์อนุญาตการใช้งานเครือข่ายท้องถิ่น (Local Network Permission บน iOS 14+) และสิทธิ์การรัน Foreground Service / Notification บน Android 13+ เพื่อรักษาการเชื่อมต่อ Socket

## 1.4 ประโยชน์ที่ได้รับ (Expected Benefits)

1. **ด้านประสิทธิภาพและเวลา:** ลดขั้นตอนการย้ายข้อความและไฟล์ระหว่างอุปกรณ์ลงมากกว่า 70% (จาก 5–6 ขั้นตอนเหลือ 1–2 ขั้นตอน) ช่วยเพิ่มความต่อเนื่องในการทำงาน (Continuity Workflow)
2. **ด้านความเร็วและคุณภาพข้อมูล:** สามารถส่งไฟล์ขนาดใหญ่ได้เต็มศักยภาพของเครือข่ายท้องถิ่นโดยไม่ถูกจำกัดด้วยความเร็วอินเทอร์เน็ต และรักษาความละเอียดไฟล์ภาพ/วิดีโอระดับต้นฉบับ 100% ปราศจากการบีบอัดซ้ำ
3. **ด้านความปลอดภัยและความเป็นส่วนตัว:** ข้อมูลผู้ใช้ไม่ไหลออกสู่เครือข่ายภายนอก ป้องกันการดักรับข้อมูลบนคลาวด์ของบุคคลที่สาม และป้องกันการรั่วไหลของข้อมูลอ่อนไหวผ่านระบบ Sensitive Filtering
4. **ด้านค่าใช้จ่ายและความสะดวก:** ใช้งานได้ฟรีโดยไม่ต้องสมัครสมาชิก ไม่ต้องใช้อินเทอร์เน็ต และไม่ต้องเชื่อมต่ออุปกรณ์ผ่านสายเคเบิลหรือแฟลชไดรฟ์

## 1.5 คำศัพท์และคำย่อที่เกี่ยวข้อง (Definitions, Acronyms and Abbreviations)

| คำศัพท์ / คำย่อ | คำเต็ม | ความหมายและนิยามเชิงเทคนิค |
|---|---|---|
| **P2P** | Peer-to-Peer | สถาปัตยกรรมเครือข่ายที่อุปกรณ์สื่อสารกันโดยตรงโดยไม่ต้องมีเซิร์ฟเวอร์กลาง |
| **mDNS / DNS-SD** | Multicast DNS / DNS Service Discovery | โปรโตคอลค้นหาและประกาศบริการของอุปกรณ์บนเครือข่ายท้องถิ่นผ่านพอร์ต UDP 5353 |
| **TLS 1.3** | Transport Layer Security 1.3 | มาตรฐานความปลอดภัยระดับการขนส่งที่ใช้เข้ารหัสข้อมูลทั้งช่องทาง Control และ Data Plane |
| **ECDSA P-256** | Elliptic Curve Digital Signature Algorithm (secp256r1) | อัลกอริทึมลายเซ็นดิจิทัลและกุญแจประจำตัวของอุปกรณ์ (Device Identity) ที่รองรับระดับฮาร์ดแวร์ครบทุก OS (Secure Enclave, Keystore API 29+, Windows CNG/DPAPI) ตาม ADR-006 |
| **SAS** | Short Authentication String | รหัสตัวเลขสั้น 6 หลักที่สร้างขึ้นจากการแลกเปลี่ยนกุญแจแบบ Commit-then-Reveal เพื่อให้ผู้ใช้ตรวจสอบด้วยตา ป้องกันการโจมตีแบบ MITM |
| **MITM** | Man-in-the-Middle Attack | รูปแบบการโจมตีที่ผู้ไม่ประสงค์ดีแทรกตัวอยู่ระหว่างกลางช่องทางการสื่อสาร |
| **HLC** | Hybrid Logical Clock | นาฬิกาเชิงตรรกะแบบผสมที่ผสานเวลาจริง (Physical Wall Clock) และตัวนับเชิงตรรกะ เพื่อแก้ปัญหานาฬิกาคลาดเคลื่อนและแก้ปัญหาการคัดลอกใหม่บนเครื่องออฟไลน์ถูกทิ้ง (ADR-008) |
| **LWW** | Last-Writer-Wins | นโยบายการระงับข้อขัดแย้งของข้อมูลโดยยึดข้อมูลที่มีค่า HLC ล่าสุดเป็นหลัก |
| **SSIM** | Structural Similarity Index Measure | ดัชนีทางคณิตศาสตร์สำหรับวัดระดับความเหมือนของโครงสร้างภาพดิจิทัล (ค่าสูงสุดเท่ากับ 1.0) |
| **Concealed Content**| Concealed Clipboard Content | ข้อมูลคลิปบอร์ดที่ถูกระบุ Flag ว่าเป็นข้อมูลลับหรือรหัสผ่านจากโปรแกรมจัดการรหัสผ่าน |
| **TTL** | Time-To-Live | กลไกกำหนดระยะเวลาคงอยู่ของข้อมูลคลิปบอร์ดชั่วคราว ก่อนถูกล้างทิ้งอัตโนมัติ |
| **Control Plane** | Control Plane Channel | ช่องทางการสื่อสารสำหรับส่งข้อความควบคุมและคลิปบอร์ดขนาดเล็ก (ผ่าน WebSocket) |
| **Data Plane** | Data Plane Channel | ช่องทางการสื่อสารสำหรับสตรีมไฟล์ขนาดใหญ่และรูปภาพ (ผ่าน HTTP Chunked) |

# บทที่ 2 การเก็บรวบรวมข้อมูล (Information Gathering)

## 2.1 กลุ่มเป้าหมาย (Target Users)

### 2.1.1 นิยามกลุ่มเป้าหมายหลัก
ผู้ใช้งานคอมพิวเตอร์และสมาร์ตโฟนที่มีอุปกรณ์ประจำตัวมากกว่าหนึ่งเครื่อง โดยมีอุปกรณ์อย่างน้อย 2 เครื่องที่ทำงานบนระบบปฏิบัติการต่างค่ายกัน และมีความจำเป็นต้องถ่ายโอนข้อมูล ข้อความ ลิงก์ หรือไฟล์ระหว่างอุปกรณ์ของตนเองเป็นประจำ

### 2.1.2 คุณลักษณะของกลุ่มเป้าหมาย (User Characteristics)
* **รูปแบบอุปกรณ์ที่ถือครอง:** (1) macOS + Windows PC, (2) Windows PC + iPhone, (3) MacBook + Android Smartphone หรือ (4) ครอบครองครบทั้ง 3–4 แพลตฟอร์ม
* **พฤติกรรมการใช้งาน:** มีความถี่ในการคัดลอกข้อความ ลิงก์ รหัส หรือไฟล์ข้ามอุปกรณ์ตั้งแต่ 5 ครั้งขึ้นไปต่อวัน
* **สภาพแวดล้อม:** ใช้งานในบ้าน คอนโดมิเนียม หรือสำนักงานที่มีระบบเครือข่าย Wi-Fi/LAN ส่วนบุคคล
* **ระดับความรู้ทางเทคนิค:** ระดับพื้นฐานถึงระดับสูง สามารถติดตั้งโปรแกรมลงเครื่องได้ด้วยตนเอง
* **ความกังวล:** ให้ความสำคัญสูงต่อความเร็ว ความสมบูรณ์ของไฟล์ และความเป็นส่วนตัวของข้อมูลส่วนบุคคล

### 2.1.3 บุคลิกภาพตัวแทนผู้ใช้งาน (User Personas)
1. **Persona 1: นักพัฒนาซอฟต์แวร์ / นักศึกษาไอที (Developer / IT Student)**
   - *พฤติกรรม:* ใช้ MacBook เขียนโค้ด แต่ใช้ Windows PC สำหรับรันงานประมวลผลหรือเล่นเกม
   - *Pain Point:* ต้องคัดลอกโค้ด, ลิงก์ API, รหัส Token ข้ามไปมาระหว่างวัน เบื่อหน่ายขั้นตอนการสลับหน้าจอส่งผ่านแอปแชต
2. **Persona 2: คอนเทนต์ครีเอเตอร์ / ดีไซเนอร์ (Digital Creator / Designer)**
   - *พฤติกรรม:* ใช้สมาร์ตโฟนถ่ายวิดีโอ 4K และรูปภาพ แต่ตัดต่อและออกแบบบนคอมพิวเตอร์ Desktop
   - *Pain Point:* ไฟล์ภาพและวิดีโอถูกลดทอนความละเอียดเมื่อส่งผ่านแอปแชต และการอัปโหลดขึ้นคลาวด์ใช้เวลานานมาก
3. **Persona 3: พนักงานออฟฟิศทั่วไป (General Office Worker)**
   - *พฤติกรรม:* ใช้คอมพิวเตอร์ Windows ที่ทำงาน แต่ใช้ iPhone ในชีวิตประจำวัน
   - *Pain Point:* ต้องการส่งภาพหน้าจอหรือข้อความสั้น ๆ ข้ามเครื่องอย่างรวดเร็ว โดยไม่ต้องการให้ข้อมูลส่วนตัวหรือเอกสารหลุดไปค้างบนเซิร์ฟเวอร์ภายนอก

|---|---|---|---|

| **M3** | การสังเกตการณ์การใช้งานจริง<br>(Contextual Inquiry) | ผู้ใช้งานจริงจำนวน 6 คน | กำหนดโจทย์ทดสอบ 5 สถานการณ์ (S1: ส่ง URL, S2: ส่งภาพหน้าจอ, S3: ส่งไฟล์ 2 GB, S4: ส่งข้อความมือถือสู่ PC, S5: ส่งภาพ PC สู่มือถือ) จับเวลาและนับจำนวนคลิก/ขั้นตอนการโต้ตอบ (แผนดำเนินงานสัปดาห์ที่ 3) |
| **M4** | การวิเคราะห์ระบบเปรียบเทียบ<br>(Competitive Analysis) | ซอฟต์แวร์ 5 ระบบ (LocalSend, KDE Connect, AirDrop, Phone Link, ClipCascade) | ติดตั้ง ทดสอบใช้งานจริง และทำตารางประเมินขีดความสามารถด้านความเร็ว การรองรับแพลตฟอร์ม การซิงก์คลิปบอร์ด และความปลอดภัย (แผนดำเนินงานสัปดาห์ที่ 2–3) |

## 2.3 ผลหรือข้อสรุปที่ได้จากการเก็บข้อมูล (Synthesis & Requirements)

### 2.3.1 ปัญหาการดำเนินการปัจจุบัน (As-Is Problems)
* **P-01 (ขั้นตอนซ้ำซ้อนสูง):** การย้ายข้อมูลทั่วไปต้องผ่านกระบวนการ 5–6 ขั้นตอน ส่งผลให้เสียเวลาสะสมในแต่ละวัน
* **P-02 (คอขวดด้านความเร็ว):** การส่งไฟล์ 2 GB ผ่านคลาวด์หรือแชตต้องใช้เวลาเฉลี่ยมากกว่า 10–15 นาที เนื่องจากความเร็วถูกจำกัดโดยค่า Upload Speed ของอินเทอร์เน็ต
* **P-03 (คุณภาพไฟล์เสียหาย):** รูปภาพและวิดีโอถูกลดทอนความละเอียดเนื่องจากบริการตัวกลางทำการบีบอัดไฟล์ซ้ำ
* **P-04 (ความเสี่ยงข้อมูลหลุด):** ผู้ใช้ส่วนใหญ่จำใจส่งรหัสผ่าน Token หรือข้อมูลส่วนบุคคลผ่านแชตหาตนเองเนื่องจากไม่มีทางเลือกอื่นที่สะดวกรวดเร็วเพียงพอ
* **P-05 (ซอฟต์แวร์เดิมมี Friction สูง):** โปรแกรมส่งไฟล์ P2P ในปัจจุบันบังคับให้ผู้ใช้ต้องกดยืนยันการรับทุกครั้ง และไม่มีระบบ Passive Clipboard Sync ข้ามค่าย
* **P-06 (ปัญหาความเข้ากันได้ของภาพในคลิปบอร์ด):** การคัดลอกรูปภาพข้ามระหว่าง macOS และ Windows มักสูญเสียความโปร่งใส (Alpha Channel) หรือวางภาพไม่ติดเนื่องจากโครงสร้างไบนารีระดับ OS แตกต่างกัน

### 2.3.2 ข้อมูลที่เกี่ยวข้องกับระบบ (System Data Requirements)
ระบบต้องประมวลผลและจัดเก็บเอนทิตีข้อมูล 6 กลุ่ม ดังต่อไปนี้:

| กลุ่มข้อมูล (Entity) | รายการข้อมูล (Attributes) | รูปแบบ / โครงสร้าง | สถานะการจัดเก็บ |
|---|---|---|---|
| **E-01: อัตลักษณ์อุปกรณ์<br>(Device Identity)** | Device ID (UUID), Device Name, Platform OS, ECDSA P-256 Private Key, X.509 Certificate | JSON / Key Storage | บันทึกถาวรใน Secure Key Storage (Keychain/DPAPI/Keystore) |
| **E-02: อุปกรณ์ที่เชื่อถือ<br>(Trusted Device Store)** | Device ID, Peer Name, Fingerprint (SHA-256), Paired Date, Status | JSON Encrypted File | บันทึกถาวรลงในไฟล์ที่เข้ารหัสในเครื่อง |

### 2.3.3 ความต้องการของผู้ใช้ (User Requirements: UR)
*นิยาม: ความต้องการ ความคาดหวัง และเป้าหมายการทำงานจากมุมมองของผู้ใช้งาน (User Perspective)*

* **UR-01 (ความสะดวกของคลิปบอร์ด):** ผู้ใช้ต้องการให้ข้อความ ลิงก์ หรือรูปภาพที่คัดลอกจากเครื่องหนึ่ง ไปพร้อมใช้งานบนคลิปบอร์ดของอีกเครื่องหนึ่งได้ทันทีโดยไม่ต้องเปิดแอปขึ้นมากดส่ง
* **UR-02 (ความเร็วในการส่งไฟล์):** ผู้ใช้ต้องการส่งไฟล์ขนาดใหญ่ข้ามเครื่องได้ด้วยความเร็วสูงของเครือข่ายภายใน โดยไม่ถูกจำกัดด้วยความเร็วอินเทอร์เน็ต
* **UR-03 (ความสมบูรณ์ของคุณภาพไฟล์):** ผู้ใช้ต้องการให้รูปภาพและไฟล์ที่โอนย้ายคงความสมบูรณ์และคุณภาพระดับต้นฉบับ 100% ปราศจากการบีบอัดซ้ำ
* **UR-04 (การควบคุมความเป็นส่วนตัว):** ผู้ใช้ต้องการให้ข้อมูลวิ่งอยู่เฉพาะในเครือข่ายส่วนตัว โดยไม่วิ่งออกอินเทอร์เน็ต และไม่มีการเก็บประวัติบนคลาวด์ภายนอก
* **UR-05 (การรับไฟล์แบบลดแรงเสียดทาน):** ผู้ใช้ต้องการรับไฟล์เข้าเครื่องของตนเองได้อัตโนมัติ โดยไม่ต้องคอยกดยืนยันทุกครั้งสำหรับอุปกรณ์ที่ตนเองจับคู่ไว้แล้ว
* **UR-06 (การทำงานแบบไม่รบกวน):** ผู้ใช้ต้องการให้โปรแกรมเปิดทำงานพร้อมระบบปฏิบัติการและทำงานอยู่เบื้องหลังเงียบ ๆ โดยไม่แสดงหน้าต่างกวนใจ
* **UR-07 (การตั้งค่าที่ง่ายดาย):** ผู้ใช้ต้องการใช้งานได้ทันทีโดยไม่ต้องลงทะเบียนเปิดบัญชีผู้ใช้ และไม่ต้องจดจำรหัสผ่าน
* **UR-08 (ความปลอดภัยของข้อมูลลับ):** ผู้ใช้ต้องการให้ระบบป้องกันการซิงก์รหัสผ่านจากโปรแกรมจัดการรหัสผ่านข้ามเครื่องโดยไม่ได้ตั้งใจ
* **UR-09 (การค้นพบอุปกรณ์อัตโนมัติ):** ผู้ใช้ต้องการให้ระบบค้นหาอุปกรณ์อื่นเจอเองโดยไม่ต้องค้นหาหรือพิมพ์หมายเลข IP Address
* **UR-10 (ความต่อเนื่องเมื่อเครือข่ายหลุด):** ผู้ใช้ต้องการให้ระบบสามารถส่งไฟล์ขนาดใหญ่ต่อจากจุดเดิมได้ทันทีเมื่อสัญญาณ Wi-Fi หลุดแล้วกลับมาเชื่อมต่อใหม่
* **UR-11 (การจัดการและเพิกถอนสิทธิ์):** ผู้ใช้ต้องการสามารถเพิกถอนการเชื่อมต่อของอุปกรณ์ที่สูญหายหรือเลิกใช้งานแล้วออกจากระบบได้ทันที

*นิยาม: ชุดคุณลักษณะ ขีดความสามารถ และโมดูลบริการหลักระดับระบบ (High-Level Capabilities) ที่พัฒนาขึ้นมาเพื่อตอบสนองต่อ User Requirements*

|---|---|---|---|
| **SF-01** | **ระบบค้นหาอุปกรณ์แบบไร้การกำหนดค่า**<br>(Zero-Configuration Discovery) | บริการค้นหา ประกาศตัวตน และตรวจจับอุปกรณ์ภายใน Subnet อัตโนมัติผ่าน mDNS พร้อมกลไกสำรองด้วย QR Code และ Manual IP | UR-07, UR-09 |

| **SF-03** | **ระบบซิงก์คลิปบอร์ดแบบเรียลไทม์**<br>(Real-Time Clipboard Sync Engine) | กลไกตรวจจับการเปลี่ยนแปลงของคลิปบอร์ดระดับ OS และส่งข้อมูลข้ามเครื่องทันที พร้อมกลไกป้องกันการวนซ้ำ (Loop Prevention) และจัดลำดับด้วย Hybrid Logical Clock (HLC) ป้องกันปัญหาข้อมูลออฟไลน์ถูกทับ | UR-01, UR-06 |

| **SF-05** | **ระบบคัดกรองข้อมูลส่วนบุคคลและข้อมูลอ่อนไหว**<br>(Privacy-Aware Sensitive Filtering) | ระบบตรวจสอบ Flag ข้อมูลลับจาก Password Managers เพื่อระงับการส่งออก พร้อมระบบตัวจับเวลาทำลายข้อมูลชั่วคราว (TTL Engine) | UR-04, UR-08 |
| **SF-06** | **ระบบสตรีมมิ่งไฟล์ความเร็วสูง**<br>(High-Throughput Streaming File Transfer) | กลไกการอ่านและส่งไฟล์แบบ Binary Chunking (1 MiB) ผ่าน HTTP/1.1 over TLS 1.3 แบบหน่วยความจำคงที่ รองรับการส่งต่อจุดเดิม (Resume ด้วย 64 MiB Checkpoints) และตรวจ Checksum | UR-02, UR-03, UR-10 |
| **SF-07** | **ระบบรับไฟล์อัตโนมัติแบบไร้การคลิก**<br>(Zero-Click Trusted File Acceptance) | บริการตรวจสอบสิทธิ์อุปกรณ์ที่จับคู่แล้วและบันทึกไฟล์ลงดิสก์ปลายทางโดยอัตโนมัติ พร้อมส่วนติดต่อผู้ใช้แบบ Drag-and-Drop Dropzone | UR-05, UR-06 |

# บทที่ 3 การวิเคราะห์ระบบ (System Analysis)

## 3.1 ภาพรวมของระบบ (System Overview)

### 3.1.1 สถาปัตยกรรมการทำงาน
DropClip ได้รับการออกแบบภายใต้สถาปัตยกรรม **Peer-to-Peer ไร้เซิร์ฟเวอร์กลาง (Fully Decentralized Architecture)** ทุกโหนดในเครือข่ายทำหน้าที่เป็นทั้ง Client และ Server (Servent) ในเวลาเดียวกัน โดยแบ่งสถาปัตยกรรมการทำงานออกเป็น 3 เลเยอร์หลัก:
1. **Discovery Layer:** ใช้โปรโตคอล mDNS/DNS-SD (UDP 5353) ในการค้นหาและแลกเปลี่ยนสถานะโหนดภายในเครือข่ายท้องถิ่นวงเดียวกัน
2. **Control Plane:** สื่อสารสองทิศทางแบบเรียลไทม์ผ่าน WebSocket over TLS 1.3 สำหรับรับส่งข้อความควบคุม (Signaling), ข้อมูลคลิปบอร์ดขนาดเล็ก (Payload ≤ 32 KiB), และ Metadata ของไฟล์
3. **Data Plane:** สตรีมข้อมูลขนาดใหญ่ผ่าน HTTP/1.1 Chunked Transfer over TLS 1.3 สำหรับส่งไฟล์และรูปภาพขนาดใหญ่ โดยแยกช่องทางออกจาก Control Plane เพื่อป้องกันปัญหาคอขวด (Head-of-Line Blocking)

### 3.1.2 แผนภาพบริบทของระบบ (Context Diagram)
*(แสดงขอบเขตของระบบ DropClip กับภายนอก: ผู้ใช้งาน, ระบบปฏิบัติการ, ที่เก็บกุญแจความปลอดภัย OS, เครือข่าย LAN, และอุปกรณ์คู่สนทนา Peer)*
> *(หมายเหตุ: อ้างอิงแผนภาพกราฟิก Context Diagram ในเล่มรายงาน)*

### 3.1.3 กรณีการใช้งานของระบบ (Use Case Specifications)
ระบบประกอบด้วย 12 กรณีการใช้งาน (Use Cases) หลัก ครอบคลุมการทำงานร่วมกันระหว่าง 3 Actors: **ผู้ใช้งาน (End User)**, **อุปกรณ์คู่สนทนา (Peer Device)**, และ **ระบบภายใน / ระบบปฏิบัติการ (Internal Subsystems / OS)**:

| รหัส Use Case | ชื่อกรณีการใช้งาน | ผู้กระทำหลัก (Primary Actor) | เงื่อนไขก่อนเริ่ม (Pre-conditions) | คำอธิบายลำดับเหตุการณ์หลัก (Main Success Scenario) |
|---|---|---|---|---|
| **UC-01** | ค้นหาอุปกรณ์ในวง LAN<br>(Discover Peer Nodes) | End User / OS Daemon | เชื่อมต่อ LAN/Wi-Fi เดียวกัน | ระบบส่งและรับฟัง mDNS UDP 5353 นำรายชื่อโหนดมาแสดงบน Menubar/Tray UI |
| **UC-02** | จับคู่อุปกรณ์แบบ QR Code<br>(Pair via QR & SAS) | End User | ค้นพบอุปกรณ์ใน LAN | ผู้ใช้สแกน QR Code ตรวจสอบรหัส SAS 6 หลักแบบ Commit-then-Reveal และกดยืนยันทั้งสองฝั่ง |
| **UC-03** | จับคู่อุปกรณ์แบบ Manual IP + PIN<br>(Pair via Salted PIN) | End User | mDNS ถูกบล็อกหรือเชื่อมตรง | ผู้ใช้ระบุ IP + PIN 6 หลัก ระบบใช้ PIN เป็น local salt คำนวณ SAS โดยไม่ส่ง PIN บนสายเครือข่าย |
| **UC-04** | ซิงก์คลิปบอร์ดข้อความอัตโนมัติ<br>(Sync Text Passive — Tier 1) | End User (Copy/Paste) | อุปกรณ์จับคู่กันแล้ว (Trusted) | ผู้ใช้กด Copy บน macOS/Windows ระบบดักจับ ตรวจสอบ suppression ส่งผ่าน WebSocket และเขียนลงคลิปบอร์ดปลายทางทันที |
| **UC-05** | ซิงก์คลิปบอร์ดรูปภาพข้าม OS<br>(Sync Image with Normalization) | End User | อุปกรณ์จับคู่กันแล้ว | ผู้ใช้ Copy ภาพ ระบบแปลงโครงสร้าง TIFF/DIB เป็น PNG ส่งผ่าน Data Plane และสังเคราะห์ลงคลิปบอร์ดปลายทาง |
| **UC-06** | ส่งคลิปบอร์ดจากมือถือสู่เดสก์ท็อป<br>(Send Mobile Clipboard — Tier 2/3) | End User | มือถืออยู่ในวง LAN เดียวกัน | ผู้ใช้แตะ Quick Settings Tile หรือ Share Sheet ระบบดึงคลิปบอร์ดส่งไปยังเดสก์ท็อปผ่าน WebSocket |
| **UC-07** | รับคลิปบอร์ดบนมือถือ<br>(Receive Mobile Clipboard — Tier 2/3) | Peer Device (Desktop) | มือถือรัน Foreground Service / App | เดสก์ท็อปส่งข้อความมา Android เขียนลงคลิปบอร์ดอัตโนมัติ / iOS บันทึกลงคิวเพื่อนำเข้าเมื่อเปิดแอป |
| **UC-08** | กรองข้อมูลอ่อนไหวจากโปรแกรมรหัสผ่าน<br>(Filter Sensitive Content) | Password Manager / User | เปิดใช้งานระบบ DropClip | ผู้ใช้ Copy รหัสผ่านจาก Password Manager ระบบตรวจจับ Sensitive Marker และยกเลิกการส่งออก 100% |
| **UC-09** | ถ่ายโอนไฟล์ขนาดใหญ่แบบสตรีมมิ่ง<br>(Stream File / Folder Transfer) | End User | อุปกรณ์จับคู่กันแล้ว | ผู้ใช้ลากวางไฟล์ลง Dropzone ระบบส่งข้อเสนอ สตรีมไบนารีบล็อกละ 1 MiB ตรวจ Checksum และบันทึกดิสก์ |
| **UC-10** | กู้คืนและส่งไฟล์ต่อจากจุดเดิม<br>(Resume Interrupted Transfer) | Peer Device / End User | การส่งไฟล์หลุดกลางคัน | ระบบตรวจสอบ Sidecar `.part.json` ดึง Byte Offset ล่าสุด และเริ่มสตรีมส่วนที่เหลือจนสมบูรณ์ |
| **UC-11** | เพิกถอนสิทธิ์อุปกรณ์ในคลัสเตอร์<br>(Revoke Device with Signed Broadcast)| End User | ต้องการตัดอุปกรณ์ออกจากคลัสเตอร์| ผู้ใช้สั่งเพิกถอน ระบบตัดการเชื่อมต่อในเครื่อง ส่ง Signed Revocation Broadcast และแจ้งเตือนผู้ใช้ทั่วคลัสเตอร์ |
| **UC-12** | กำหนดค่าระบบและเปิดทำงานพร้อม OS<br>(System Settings & Auto-Start) | End User | ติดตั้งแอปพลิเคชันแล้ว | ผู้ใช้ปรับการตั้งค่า (โฟลเดอร์ปลายทาง, TTL, Auto-Start) ระบบบันทึกและลงทะเบียน service กับ OS |

*นิยาม: ข้อกำหนดพฤติกรรมและการทำงานจำเพาะระดับฟังก์ชัน (System Software Behavioral Functions) ที่ระบบต้องปฏิบัติการ*

#### FR-01: การค้นหาและประกาศตัวตนบนเครือข่าย (Zero-Configuration Node Discovery)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** เพื่อให้อุปกรณ์ในคลัสเตอร์ตรวจจับและค้นพบกันเองได้โดยอัตโนมัติบนวง Subnet เดียวกัน ตัดความจำเป็นที่ผู้ใช้ต้องจำหรือพิมพ์หมายเลข IP Address (ตอบสนอง UR-07, UR-09)
* **Verification Method:** Test (T) & Demonstration (D) — ทดสอบการส่งและแยกวิเคราะห์ mDNS UDP 5353 พร้อมสาธิตการปรากฏของอุปกรณ์บน UI ภายใน 3 วินาที
* **Description:** ระบบต้องประกาศบริการและค้นหาอุปกรณ์ DropClip อื่น ๆ ในเครือข่ายท้องถิ่นวงเดียวกันโดยอัตโนมัติ
* **Input:** สัญญาณ mDNS Multicast Announcement Packet บนพอร์ต UDP 5353
* **Process:**
  1. เมื่อเริ่มต้น ระบบเปิดรับฟังและส่ง Multicast Packet บน UDP พอร์ต 5353 ตามมาตรฐาน RFC 6762 / 6763
  2. ประกาศ Service Type `_dropclip._tcp` พร้อมแนบ TXT Record (ระบุ Device ID, Device Name ที่เข้ารหัส Base64, Platform OS, Port, และ Fingerprint)
  3. เมื่อได้รับแพ็กเก็ตจากโหนดอื่น ให้แยกวิเคราะห์ข้อมูลและตรวจสอบกับฐานข้อมูล Trusted Device Store
  4. อัปเดตรายชื่อใน Discovered Peer Cache หากไม่ได้รับสัญญาณจากโหนดใดเกิน 30 วินาที ให้ทำเครื่องหมายว่า Stale และลบออกจากรายการเมื่อเกิน 120 วินาที
* **Output:** รายชื่ออุปกรณ์ที่ออนไลน์ สถานะการจับคู่ และข้อมูลการเชื่อมต่อพร้อมแสดงผลบน UI
* **Data Validation:** ตรวจสอบรูปแบบ Protocol Version และความถูกต้องของแพ็กเก็ต mDNS ทิ้งแพ็กเก็ตที่มีโครงสร้างผิดเพี้ยน
* **Access Control:** ข้อมูลใน TXT Record ต้องเป็นข้อมูลสาธารณะเท่านั้น ห้ามบรรจุ Private Key หรือ Secret ใด ๆ

### FR-02: การจับคู่อุปกรณ์และการแลกเปลี่ยนกุญแจ (Secure Device Pairing & Key Exchange)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** สร้างความเชื่อถือระดับการเข้ารหัสสองทิศทาง (Mutual Trust) และตัดความเสี่ยง Man-in-the-Middle (MITM) อย่างสมบูรณ์ผ่าน Visual Out-of-Band Channel และ Commit-then-Reveal โดยไม่มีการส่ง PIN หรือค่าที่ derive จาก PIN ผ่านเครือข่าย (ตอบสนอง UR-04, UR-07)
* **Verification Method:** Test (T) & Inspection (I) — ตรวจสอบความถูกต้องของรหัส SAS เทียบกับ Test Vector และตรวจ Network Packet Capture ว่าไม่มี PIN รั่วไหล
* **Description:** ระบบต้องอนุญาตให้ผู้ใช้สร้างความเชื่อถือระหว่างอุปกรณ์สองเครื่องผ่านการแลกเปลี่ยนกุญแจ ECDSA P-256 และยืนยันรหัส SAS แบบ Commit-then-Reveal พร้อมรองรับ Manual PIN Mode ที่ปราศจากการส่ง PIN บนสายเครือข่าย เพื่อป้องกันการโจมตี Active MITM Brute-force
* **Input:** ข้อมูล QR Code Payload (IP, Port, Fingerprint, Nonce_A, Expire Time) หรือการระบุ Host IP + PIN 6 หลัก และการยืนยันรหัสจากผู้ใช้
* **Process (Commit-then-Reveal Scheme & Zero PIN on Wire):**
  1. อ้างอิงข้อกำหนดทางคณิตศาสตร์และลำดับ Handshake ตาม **Protocol Spec §5.4 และ §5.5** เป็นศูนย์กลางความถูกต้อง
  2. เครื่องริเริ่ม (Host) สุ่มสร้างค่า `nonce_A` 16 ไบต์ (CSPRNG) กำหนดอายุ 60 วินาที แสดงผ่าน QR Code บนหน้าจอ หรือแสดง PIN 6 หลักในโหมด Manual PIN
  3. เครื่องที่สอง (Client) ได้รับ `nonce_A` ผ่านการสแกน QR Code (หรือผู้ใช้พิมพ์ PIN 6 หลักในโหมด Manual โดยระบบ Client ห้ามส่งค่า PIN หรือ Hash ของ PIN บนเครือข่ายเด็ดขาด)
  4. Client สุ่มค่า `nonce_B` 16 ไบต์ และส่ง Commitment $C_B = \text{SHA-256}(\text{"dropclip-commit-v1:"} \parallel nonce_B \parallel fp_B)$ ผ่าน `POST /api/v1/pair` ใน mTLS Handshake ไปยัง Host
  5. Client เปิดเผย `nonce_B` ผ่าน `POST /api/v1/pair/confirm`; Host ตรวจสอบความถูกต้องของ Commitment $C_B$
  6. ทั้งสองฝั่งคำนวณรหัสตัวเลข 6 หลัก (Short Authentication String - SAS):
     - *QR Mode:* $\text{SAS} = \text{SHA-256}(fp_{lo} \parallel fp_{hi} \parallel nonce_A \parallel nonce_B) \bmod 10^6$
     - *Manual PIN Mode (Zero PIN on Wire):* $\text{SAS} = \text{SHA-256}(fp_{lo} \parallel fp_{hi} \parallel nonce_A \parallel nonce_B \parallel \text{"dropclip-pin-salt-v1:"} \parallel \text{UTF8}(\text{PIN})) \bmod 10^6$
  7. แสดงรหัส SAS บนหน้าจอทั้งสองเครื่องเพื่อให้ผู้ใช้ตรวจสอบความตรงกันด้วยตาเปล่า และส่ง `POST /api/v1/pair/finalize` เมื่อผู้ใช้กดปุ่มยืนยันทั้งสองฝั่ง บันทึก Key Fingerprint ลงใน Trusted Device Store ถาวร
* **Output:** อุปกรณ์ทั้งสองเข้าสู่สถานะ Paired/Trusted และเปิดช่องทาง WebSocket สื่อสารที่ปลอดภัย
* **Data Validation:** ตรวจสอบอายุของ Nonce (หมดอายุใน 60 วินาที), ค่า Commitment และรูปแบบ Key Fingerprint (Hex 64 ตัวอักษร)
* **Access Control & Security:** 
  - ห้ามส่ง PIN หรือค่าที่ derive มาจาก PIN ผ่านสายเครือข่ายเด็ดขาด เพื่อตัดการโจมตีแบบ Offline Dictionary Attack (10^6 ค่า)
  - จำกัดอัตราการขอจับคู่ไม่เกิน 5 ครั้งต่อนาทีต่อหนึ่ง IP Address
  - หากกดยืนยันรหัสผิดพลาดหรือ commitment ล้มเหลวติดต่อกัน 3 ครั้ง ระบบต้องระงับการเชื่อมต่อจาก IP นั้นเป็นเวลา 5 นาที

### FR-03A: การซิงก์คลิปบอร์ดระดับ Tier 1 — Full Passive (macOS & Windows)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** หัวใจหลักของประสบการณ์ Desktop Continuity มอบการทำงานแบบ Zero-Interaction คัดลอกและวางได้ทันทีข้ามระหว่าง macOS และ Windows (ตอบสนอง UR-01, UR-06)
* **Verification Method:** Test (T) & Demonstration (D) — ทดสอบการดักจับ Event วัดค่าความหน่วง Latency p95 < 1,000 ms และสาธิตการกด Copy/Paste ข้ามระบบ
* **Description:** ระบบต้องเฝ้าติดตามและซิงก์ข้อมูลคลิปบอร์ดสองทิศทางระหว่าง macOS และ Windows โดยอัตโนมัติในเบื้องหลังโดยไม่ต้องอาศัยการกดปุ่มใด ๆ จากผู้ใช้
* **Target Platform:** macOS 12.0 ขึ้นไป, Windows 10 (Build 19041) ขึ้นไป
* **Pre-conditions:** อุปกรณ์ทั้งสองต้องจับคู่กันสำเร็จ (Trusted State) และเชื่อมต่อผ่าน WebSocket Control Plane สมบูรณ์
* **Input:** เหตุการณ์การคัดลอกข้อมูลในระดับระบบปฏิบัติการ (OS Clipboard Change Event)
* **Process:**
  1. *ฝั่งตรวจจับการเปลี่ยนแปลง:*
     - บน Windows: รับ Event ผ่าน Win32 API `AddClipboardFormatListener` (Event-driven อัตรากิน CPU < 0.2%)
     - บน macOS: ตรวจสอบค่า `changeCount` ของ `NSPasteboard` ด้วยกลไก Adaptive Polling (200 ms เมื่อผู้ใช้ Active, 1,000 ms เมื่อ Idle, 2,000 ms เมื่อล็อกหน้าจอ)
  2. *ฝั่งส่ง:* ตรวจสอบ Suppression Window (800 ms และค่า Hash ต้องไม่ตรงกับข้อมูลที่เพิ่งเขียน) หากผ่านเกณฑ์ ให้ส่งข้อมูลพร้อมค่า Hybrid Logical Clock (HLC) ไปยังเครื่องปลายทางผ่าน WebSocket
  3. *ฝั่งรับ:* ผสานค่า HLC, ตรวจสอบลำดับด้วยนโยบาย Last-Writer-Wins (LWW บน HLC), บันทึก Hash ลง Suppression Table และเขียนข้อมูลลง System Clipboard ของเครื่องปลายทางทันที
* **Output:** ข้อมูลปรากฏในคลิปบอร์ดของเครื่องปลายทาง พร้อมใช้งานด้วยคำสั่ง Paste (Ctrl+V / Cmd+V) ทันที
* **Data Routing Threshold:** 
  - ข้อความ Plain Text ขนาด $\le 32\text{ KiB}$: ส่งแบบ Inline ผ่าน WebSocket Control Plane Frame ทันที
  - ข้อความ Plain Text ขนาด $> 32\text{ KiB}$ และข้อมูลรูปภาพทั้งหมด: บันทึกเป็น Blob ชั่วคราว และสลับไปส่งผ่าน HTTP Chunked Data Plane
* **Exception Handling:** หากเกิดเหตุการณ์ Clipboard Access Lock จากแอปพลิเคชันอื่น ให้หน่วงเวลาและพยายามเข้าถึงใหม่ (Retry with Backoff) สูงสุด 3 ครั้ง หากไม่สำเร็จให้บันทึก Warning Log โดยไม่ทำให้โปรแกรม Crash

### FR-03B: การซิงก์คลิปบอร์ดระดับ Tier 2 — Assisted Sync (Android 10+)
* **Priority:** Should Have (MoSCoW)
* **Rationale:** มอบประสบการณ์ Continuity สูงสุดบนระบบปฏิบัติการ Android ภายใต้ข้อจำกัดความเป็นส่วนตัวของ Android 10+ ที่ไม่อนุญาตให้อ่านคลิปบอร์ดเบื้องหลัง (ตอบสนอง UR-01, UR-06)
* **Verification Method:** Test (T) & Demonstration (D) — ทดสอบบน Android Emulator/อุปกรณ์จริง ตรวจสอบการส่งผ่าน Quick Settings Tile และ Notification
* **Description:** ระบบต้องรองรับการเขียนข้อมูลคลิปบอร์ดที่ส่งมาจาก Desktop ลงสู่ Android อัตโนมัติ และรองรับการดึงข้อมูลคลิปบอร์ดจาก Android ส่งกลับไปยัง Desktop ผ่านการสั่งการแบบขั้นตอนเดียว (1-Click Action)
* **Target Platform:** Android 10 (API Level 29) ถึง Android 15
* **Pre-conditions:** แอปพลิเคชัน DropClip เปิดทำงาน Foreground Service (`foregroundServiceType="connectedDevice"` ตาม ADR-007) พร้อมแสดง Persistent Notification และได้รับสิทธิ์เครือข่ายแล้ว
* **Input:**
  - *ทิศทาง Inbound (Desktop → Android):* ข้อความ `clipboard.update` ผ่าน WebSocket
  - *ทิศทาง Outbound (Android → Desktop):* สัญญาณการคลิกจาก Quick Settings Tile, ปุ่มบน Notification หรือการแชร์ข้อความผ่าน Share Sheet
* **Process:**
  1. *ทิศทาง Inbound (อัตโนมัติ):*
     - Foreground Service รับข้อมูลจาก WebSocket Control Plane
     - นำข้อมูลข้อความหรือ URI บรรจุลง `ClipData`
     - เรียกคำสั่ง `ClipboardManager.setPrimaryClip()` เพื่อเขียนลงคลิปบอร์ดของ Android ทันที
     - แสดงการแจ้งเตือนแบบเงียบ (Silent Toast/HUD) แจ้งผู้ใช้ว่า "คัดลอกจาก [Device Name] แล้ว"
  2. *ทิศทาง Outbound (Assisted):*
     - เมื่อผู้ใช้แตะ **Quick Settings Tile ("DropClip")** หรือแตะปุ่ม **"Send Clipboard"** บน Persistent Notification
     - ระบบจะเรียกคำสั่งผ่าน `PendingIntent` (Android 14+ API Requirement) ดึง Transient Activity ขึ้นมาระดับเบื้องหน้าในเสี้ยววินาทีเพื่อรับ Transient Focus
     - อ่านข้อมูลจาก `ClipboardManager.getPrimaryClip()`
     - ส่งข้อมูลต่อไปยังอุปกรณ์ Desktop ที่เชื่อมต่ออยู่ผ่าน WebSocket Control Plane
* **Output:** ข้อมูลซิงก์ถึงกันทั้งสองฝั่งอย่างถูกต้องตามข้อกำหนดความปลอดภัยของระบบปฏิบัติการ
* **Data Validation:** ตรวจสอบ `ClipDescription.EXTRA_IS_SENSITIVE` หากพบว่าข้อมูลถูกตั้งค่าเป็นข้อมูลลับ ให้ยกเลิกการส่งออกทันที
* **Discovery Constraint:** ระบบต้องทำการ Acquire `WifiManager.MulticastLock` ระหว่างทำการสแกน mDNS เพื่อรับฟังแพ็กเก็ต UDP 5353 ได้อย่างสมบูรณ์
* **Exception Handling:** หาก Service ถูกระบบปฏิบัติการตัดการทำงาน ให้ลงทะเบียนคำสั่ง `START_STICKY` เพื่อให้ Foreground Service ฟื้นตัวกลับมาโดยอัตโนมัติ

### FR-03C: การซิงก์คลิปบอร์ดระดับ Tier 3 — Manual-Assist Sync (iOS 15+)
* **Priority:** Could Have (MoSCoW — Assisted Stretch Target)
* **Rationale:** มอบช่องทางการทำงานร่วมกับอุปกรณ์ iOS 15+ ภายใต้ข้อจำกัดเข้มงวดของ Apple Sandbox, Paste Permission Prompt, และ Memory Quota (ตอบสนอง UR-01, UR-06)
* **Verification Method:** Test (T) & Inspection (I) — ตรวจวัด Peak RAM < 30 MB ใน Share Extension และตรวจสอบโค้ด Native Swift
* **Description:** ระบบต้องรองรับการส่งข้อความ ลิงก์ และรูปภาพจาก iOS ไปยังอุปกรณ์อื่นผ่านส่วนขยายระบบ และรองรับการนำเข้าคลิปบอร์ดจากเครื่องอื่นอย่างปลอดภัย
* **Target Platform:** iOS 15.0 ถึง iOS 18
* **Pre-conditions:** ติดตั้งแอปพลิเคชัน DropClip และเปิดใช้งานสิทธิ์ Local Network Access
* **Input:**
  - *ทิศทาง Outbound (iOS → Others):* ข้อมูลที่ส่งผ่าน Share Sheet Extension, การกด Action Button (iPhone 15 Pro+), หรือการกดปุ่มบน Lock/Home Screen Widget
  - *ทิศทาง Inbound (Others → iOS):* สัญญาณข้อมูลที่ส่งมายังแอปขณะเปิดใช้งาน หรือผ่านการรัน Apple Shortcuts Automation
* **Process:**
  1. *ทิศทาง Outbound (Share Extension & Widget):*
     - ผู้ใช้เลือกข้อความ/ลิงก์/ภาพ แล้วกดแชร์ผ่าน **DropClip Share Extension** หรือแตะ Widget คำสั่งลัด
     - Share Extension ทำงานด้วย Native Swift ใช้ `URLSessionConfiguration.background(withIdentifier:)` ร่วมกับ App Group Shared Keychain Identity สตรีมข้อมูลไปยังปลายทางโดยควบคุม Peak RAM < 30 MB (ป้องกัน Jetsam Kill)
     - ส่ง Payload ข้อความ และปิดการเชื่อมต่อเมื่อส่งเสร็จสิ้น
  2. *ทิศทาง Inbound:*
     - เนื่องจาก iOS ไม่อนุญาตให้เขียน `UIPasteboard` จากเบื้องหลังโดยที่ผู้ใช้ไม่ได้โต้ตอบ ระบบจะใช้วิธีเก็บข้อความล่าสุดไว้ในคิว (Catch-up Queue)
     - เมื่อผู้ใช้เปิดแอป DropClip หรือแตะ Widget ดึงข้อมูล ระบบจะอ่านข้อมูลล่าสุดจากคิวและเขียนลง `UIPasteboard.general`
* **Output:** ข้อมูลถูกส่งออกหรือเขียนลง Pasteboard ของ iOS ได้อย่างถูกต้องโดยไม่ละเมิด Sandbox
* **Platform Constraints & Fallbacks:**
  - *iOS Discovery:* สื่อสาร mDNS ผ่าน `NWBrowser` และประกาศ `NSBonjourServices` (`_dropclip._tcp`) ใน `Info.plist` แทนการใช้ raw multicast UDP socket
  - *Interactive Widget & Action Button Fallback:* บน iOS 15/16 ซึ่งยังไม่มี Interactive Widget ให้ใช้กลไกแตะ Widget เพื่อ Launch เข้าสู่แอป หรือรันคำสั่งลัดผ่าน Apple Shortcuts Automation แทน
  - *iOS 16+ Allow Paste Prompt:* รองรับและนับรวมหน้าต่างยืนยันความปลอดภัยของระบบในเกณฑ์การวัดขั้นตอนการใช้งาน (Interaction Steps 1–2 ครั้ง)
* **Exception Handling:** หากผู้ใช้ปฏิเสธ Paste Prompt ระบบต้องแสดงคำแนะนำการตั้งค่าโดยไม่หยุดการทำงาน

### FR-04: การซิงก์คลิปบอร์ดและการป้องกันการวนซ้ำ (Clipboard Synchronization & Loop Prevention)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** ควบคุมไม่ให้เกิด Infinite Loop สลับส่งไปมา และรับประกัน Eventual Consistency ของข้อมูลคลิปบอร์ดทั่วคลัสเตอร์ด้วย Hybrid Logical Clock (HLC) (ตอบสนอง UR-01, UR-06)
* **Verification Method:** Test (T) & Analysis (A) — จำลองส่งข้อมูล 1,000 เหตุการณ์พร้อมกันบน 4 โหนด และวิเคราะห์ Convergence ของข้อมูล
* **Description:** ระบบต้องกระจายข้อมูลคลิปบอร์ดไปยังอุปกรณ์ที่จับคู่ พร้อมระงับการวนซ้ำของข้อมูล และผสานข้อมูลด้วยหลักการ Hybrid Logical Clock (HLC)
* **Input:** วัตถุคลิปบอร์ดที่ตรวจพบจาก FR-03A/B/C หรือข้อความ `clipboard.update` จากอุปกรณ์อื่น
* **Process (ขาส่ง):**
  1. ตรวจสอบ Suppression Window: หากอยู่ในช่วงเวลา 800 ms หลังระบบเพิ่งเขียนข้อมูลลงคลิปบอร์ด และค่าแฮชตรงกับข้อมูลที่เพิ่งเขียน ให้ยกเลิกการส่ง (ป้องกัน Echo Loop)
  2. ตรวจสอบสถานะ Concealed: หากข้อมูลติดสถานะอ่อนไหว ให้ยกเลิกการส่งทันที (FR-05)
  3. ทำการ Tick ค่า Hybrid Logical Clock (HLC: Physical Milliseconds + Logical Counter) ของเครื่องตนเอง
  4. หากข้อมูล $\le 32\text{ KiB}$ ส่งผ่าน WebSocket ทันที, หากข้อมูล $> 32\text{ KiB}$ ให้บันทึกเป็น Blob ชั่วคราวและส่งเฉพาะ Reference ID
* **Process (ขารับ):**
  1. ตรวจสอบโหนดต้นทาง: หาก `origin == myId` ให้ทิ้งข้อมูลทันที (ป้องกัน Self-Reflection Loop)
  2. ตรวจสอบ Clock Drift หากค่าเวลา `l` ของผู้ส่งล้ำหน้าเกิน 60 วินาที ให้ปฏิเสธข้อความ (`clipboard.clock_drift_exceeded`)
  3. รวมค่า HLC: `hlc = hlc.merge(remote_hlc)`
  4. ตรวจสอบ Message ID กับ LRU Cache (ขนาด 200 รายการ) หากซ้ำให้ทิ้งข้อมูล
  5. แก้ไขข้อขัดแย้งด้วยหลักการ Last-Writer-Wins (LWW) บนค่า HLC หากเท่ากัน ให้ตัดสินด้วยการเปรียบเทียบค่า Device ID
  6. ตั้งค่า Suppression Window และค่าแฮชล่าสุด ก่อนสั่งเขียนข้อมูลลงคลิปบอร์ดของระบบปฏิบัติการ
* **Output:** ข้อมูลปรากฏในคลิปบอร์ดของอุปกรณ์ปลายทางพร้อมใช้งาน โดยข้อมูลใหม่ที่คัดลอกจากเครื่องออฟไลน์จะไม่ถูกทับทิ้ง
* **Data Validation:** ตรวจสอบความสมบูรณ์ของ JSON Envelope และความถูกต้องของค่าแฮชข้อมูล

### FR-05: การคัดกรองข้อมูลลับและการทำลายข้อมูลตามกำหนดเวลา (Sensitive Content Filtering & TTL)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** ป้องกันไม่ให้รหัสผ่านหรือข้อมูลส่วนบุคคลที่คัดลอกจาก Password Managers รั่วไหลออกสู่เครือข่ายโดยไม่ตั้งใจ (ตอบสนอง UR-04, UR-08)
* **Verification Method:** Test (T) & Inspection (I) — ทดสอบคัดลอกข้อมูล 100 ครั้ง จาก 1Password, Bitwarden, KeePass, Keychain และตรวจ Wireshark Packet Trace
* **Description:** ระบบต้องตรวจจับและระงับการส่งข้อมูลอ่อนไหวจากโปรแกรมจัดการรหัสผ่าน และล้างข้อมูลชั่วคราวตามเวลาที่กำหนด
* **Input:** Metadata ชนิดคลิปบอร์ดจาก OS และค่าคอนฟิกูเรชัน TTL
* **Process:**
  1. ตรวจสอบ Flag ข้อมูลลับระดับ OS ครบ 5 รูปแบบมาตรฐาน:
     - macOS: `org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType` (รวมถึง `com.agilebits.onepassword`)
     - Windows: `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory` (เมื่อมีค่าเป็น 0 / FALSE)
     - Android: `ClipDescription.EXTRA_IS_SENSITIVE` / `Clipboard.EXTRA_IS_SENSITIVE`
  2. หากพบ Flag ดังกล่าว ให้ทำการ Drop ข้อมูลทิ้งทันที บันทึก Log เฉพาะประเภทข้อมูล (ห้ามบันทึกเนื้อหาเด็ดขาด)
  3. สำหรับข้อมูลคลิปบอร์ดทั่วไปที่มีการกำหนดค่า TTL (เช่น ข้อความสั้น 60 วินาที) ให้ตั้งตัวนับเวลาถอยหลัง
  4. เมื่อครบกำหนดเวลา TTL ระบบตรวจสอบว่าข้อมูลบนคลิปบอร์ดปัจจุบันยังคงตรงกับข้อมูลเดิมหรือไม่ หากตรงกันจึงสั่งล้างคลิปบอร์ด
* **Output:** ข้อมูลลับไม่ถูกส่งออกนอกเครื่อง และข้อมูลชั่วคราวถูกล้างตามเวลาที่กำหนด
* **Business Rule:** หากผู้ใช้คัดลอกข้อมูลใหม่อื่นทับลงไปแล้วก่อนที่ TTL จะหมดอายุ ระบบต้องยกเลิกการล้างคลิปบอร์ดนั้น

### FR-06: การแปลงโครงสร้างไบนารีภาพข้ามระบบปฏิบัติการ (Cross-OS Image Normalization)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** แก้ปัญหาความไม่เข้ากันของข้อมูลภาพในคลิปบอร์ดระหว่าง macOS และ Windows รักษา Alpha Transparency และคุณภาพของภาพระดับพิกเซล (ตอบสนอง UR-03)
* **Verification Method:** Test (T) & Demonstration (D) — คำนวณค่า SSIM เปรียบเทียบภาพต้นฉบับกับภาพปลายทาง (เป้าหมาย SSIM $\ge 0.99$) และทดสอบ Paste บน Photoshop/Paint
* **Description:** ระบบต้องแปลงข้อมูลไบนารีของรูปภาพในคลิปบอร์ดให้สอดคล้องกับโครงสร้างของระบบปฏิบัติการปลายทางโดยไม่สูญเสียคุณภาพ
* **Input:** สตรีมไบนารีรูปภาพจากคลิปบอร์ดต้นทาง
* **Process:**
  1. ตรวจสอบฟอร์แมตภาพต้นทาง: TIFF (macOS), `CF_DIB` / `CF_DIBV5` (Windows), หรือมาตรฐาน PNG
  2. หากเป็น TIFF แบบหลาย Representation ให้คัดเลือก Representation ที่มีความละเอียดสูงที่สุด
  3. หากเป็น Windows DIB ให้แปลงการเรียงสีจาก BGR เป็น RGBA และแปลงการเรียงแถวพิกเซลจาก Bottom-Up เป็นมาตรฐานสากล
  4. หากเป็น `CF_DIBV5` ให้อ่าน Bitmask เพื่อคงค่าความโปร่งใส (Alpha Transparency Channel)
  5. บรรจุเป็นภาพมาตรฐาน PNG ข้ามเครือข่าย และเมื่อเขียนลงเครื่อง Windows ปลายทาง ให้สังเคราะห์ทั้งรูปแบบ PNG และ `CF_DIBV5` เข้าสู่คลิปบอร์ดพร้อมกัน
* **Output:** ภาพในคลิปบอร์ดปลายทางสามารถกด Paste ลงในแอปพลิเคชันใด ๆ ได้อย่างถูกต้อง สมบูรณ์ทั้งสีและมิติ
* **Data Validation:** ตรวจสอบ Magic Bytes ของไฟล์รูปภาพ ปฏิเสธข้อมูลที่ Header เสียหาย

### FR-07: การส่งไฟล์แบบสตรีมมิ่งผ่าน Data Plane (High-Throughput File Transfer Sender)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** เพื่อให้การถ่ายโอนไฟล์ขนาดใหญ่ (4 GB บนมือถือ, 10 GB บน Desktop) ทำได้ด้วยความเร็วสูงเต็มประสิทธิภาพของเครือข่าย โดยใช้หน่วยความจำคงที่ ไม่ก่อให้เกิดสภาวะ Out-of-Memory (ตอบสนอง UR-02, UR-03, UR-10)
* **Verification Method:** Test (T) & Demonstration (D) — ทดสอบส่งไฟล์ 1 GB และ 10 GB วัด Throughput เทียบกับ iperf3 baseline และบันทึก Memory Profiler
* **Description:** ระบบต้องส่งไฟล์และโฟลเดอร์ในรูปแบบไบนารีสตรีมมิ่งโดยใช้หน่วยความจำคงที่ ไม่จำกัดขนาดไฟล์ตามโปรโตคอล (รองรับไฟล์ระดับ 4 GB บนมือถือ และ 10 GB บน Desktop)
* **Input:** รายการไฟล์หรือโฟลเดอร์จากการลากวาง (Drag-and-Drop) หรือการเลือกไฟล์ของผู้ใช้
* **Process:**
  1. สำรวจรายการไฟล์ โครงสร้างไดเรกทอรี และคำนวณผลรวมขนาดไฟล์ทั้งหมด พร้อมสร้าง Transfer ID
  2. ส่งข้อความ `file.offer` พร้อม Metadata (ชื่อ, ขนาด, SHA-256) ผ่าน WebSocket Control Plane
  3. เมื่อปลายทางตอบรับ เริ่มต้นเปิดการเชื่อมต่อ HTTP/1.1 POST ไปยัง Data Plane Endpoint ของปลายทาง
  4. อ่านไฟล์แบบ Stream ทีละบล็อกขนาด 1 MiB (ห้ามโหลดทั้งไฟล์เข้าหน่วยความจำ) และคำนวณแฮช SHA-256 แบบสะสม
  5. ส่งความคืบหน้า (Progress) แจ้งเตือนไปยัง UI ทุก 500 ms หรือทุก 5%
  6. เมื่อส่งครบถ้วน ส่งคำขอเสร็จสิ้นเพื่อรอรับการยืนยันความถูกต้องจากปลายทาง
* **Output:** ข้อมูลไฟล์ถูกส่งไปยังปลายทางสำเร็จ 100% พร้อมแสดงรายงานความเร็วและเวลาที่ใช้
* **Access Control:** ส่งไฟล์ได้เฉพาะอุปกรณ์ที่ยืนยันตัวตนใน Trusted Device Store แล้วเท่านั้น

### FR-08: การรับไฟล์อัตโนมัติและการตรวจสอบความถูกต้อง (Zero-Click File Receiver & Integrity Check)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** อำนวยความสะดวกในการรับไฟล์ พร้อมป้องกันการโจมตี Directory Traversal และมัลแวร์ผ่าน Path Sanitization, OS Quarantine และ Checksum Verification (ตอบสนอง UR-05, UR-06)
* **Verification Method:** Test (T) & Inspection (I) — ทดสอบ Path Traversal Attack Suite ครบ 12 รูปแบบ และตรวจสอบการแนบ Quarantine Attribute บน OS
* **Description:** ระบบต้องรับไฟล์ บันทึกข้อมูลลงดิสก์อย่างปลอดภัย และตรวจสอบความถูกต้องสมบูรณ์ของข้อมูลอัตโนมัติ (โดยมีค่าเริ่มต้นการรับไฟล์อัตโนมัติเป็น ปิด/Disabled เพื่อความปลอดภัยสูงสุด และผู้ใช้สามารถเปิดใช้งานเฉพาะอุปกรณ์ที่เชื่อถือได้)
* **Input:** HTTP Data Stream จากเครื่องส่งที่ได้รับอนุญาต
* **Process:**
  1. ตรวจสอบสิทธิ์โหนดต้นทางผ่าน TLS Certificate Pinning หากไม่ผ่านให้ตอบกลับ HTTP 403 Forbidden
  2. ทำความสะอาดพาธไฟล์ (Path Sanitization): ปฏิเสธพาธที่มี `..`, Null Byte, Absolute Path หรืออักขระต้องห้ามของ OS ครบ 12 รูปแบบ
  3. ตรวจสอบพื้นที่ว่างบนดิสก์ปลายทาง หากพื้นที่ไม่พอ ให้ยกเลิกและแจ้งเตือนผู้ใช้ (`507 E_DISK_FULL`)
  4. สตรีมข้อมูลลงไฟล์ชั่วคราว `.part` และคำนวณผลรวมแฮช SHA-256 ควบคู่ไปกับการเขียนลงดิสก์ พร้อมบันทึก Checkpoint ลง sidecar ทุก 64 MiB
  5. เมื่อสตรีมครบถ้วน เปรียบเทียบผลรวมแฮชกับค่าที่ต้นทางแจ้ง หากถูกต้องตรงกัน เปลี่ยนชื่อไฟล์จาก `.part` เป็นชื่อจริงและย้ายเข้าโฟลเดอร์ปลายทาง
  6. แสดงการแจ้งเตือน (System Notification) ให้ผู้ใช้ทราบ
* **Output:** ไฟล์ถูกบันทึกลงโฟลเดอร์ปลายทางอย่างถูกต้องสมบูรณ์
* **Security Rule:** บน macOS ต้องทำการแนบ Quarantine Attribute (`com.apple.quarantine`), บน Windows แนบ Mark-of-the-Web (`Zone.Identifier`) และห้ามมิให้ระบบสั่ง Execute หรือเปิดไฟล์โดยอัตโนมัติเด็ดขาด

### FR-09: การส่งต่อไฟล์จากจุดที่ค้าง (Resumable Transfer Handling)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** ป้องกันการสูญเสียเวลาและแบนด์วิดท์เมื่อสัญญาณ Wi-Fi ขาดหายระหว่างส่งไฟล์ขนาดใหญ่ โดยสามารถสตรีมต่อจากจุด Checkpoint ล่าสุดได้ทันที (ตอบสนอง UR-02, UR-10)
* **Verification Method:** Test (T) & Demonstration (D) — จำลองการตัดการเชื่อมต่อระหว่างสตรีมไฟล์ขนาดใหญ่ และตรวจสอบการส่งต่อจนสำเร็จโดยมี SHA-256 ตรงกับต้นฉบับ
* **Description:** ระบบต้องสามารถกู้คืนและส่งไฟล์ต่อจากจุดเดิมได้ทันทีเมื่อการเชื่อมต่อหลุดกลางคัน โดยใช้ระบบ Checkpoints ทุก 64 MiB
* **Input:** Transfer ID และ Item ID ของธุรกรรมที่ยังไม่สมบูรณ์
* **Process:**
  1. เมื่อการเชื่อมต่อเครือข่ายกลับมา โหนดต้นทางส่งคำขอสอบถามสถานะไปยังโหนดปลายทาง
  2. โหนดปลายทางอ่านข้อมูล Checkpoint ล่าสุดจาก Sidecar `.part.json` (ซึ่งบันทึกผลรวมแฮชของบล็อก 64 MiB ที่บันทึกเสร็จสมบูรณ์แล้ว) ตรวจสอบความถูกต้องของขนาดไฟล์บนดิสก์จริง และตอบกลับค่า Byte Offset ของขอบเขตบล็อกล่าสุด
  3. โหนดต้นทางเลื่อน Pointer การอ่านไฟล์ (Seek) ไปยัง Byte Offset นั้น แล้วเริ่มสตรีมข้อมูลส่วนที่เหลือ
  4. ทำการคำนวณแฮช SHA-256 แบบเต็มไฟล์เพื่อยืนยันความถูกต้องในขั้นตอนสุดท้าย
* **Output:** กระบวนการถ่ายโอนไฟล์ดำเนินต่อจนเสร็จสมบูรณ์โดยไม่ต้องส่งข้อมูลใหม่ตั้งแต่ต้น
* **Exception Handling:** หากไฟล์ `.part` บนปลายทางเสียหายหรือไม่สอดคล้องกับขนาดเดิม ให้เริ่มการส่งไฟล์นั้นใหม่ตั้งแต่ Offset 0

### FR-10: การจัดการสถานะ การตกลงเวอร์ชัน และการเชื่อมต่อใหม่อัตโนมัติ (Connection State, Protocol Negotiation & Reconnection)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** รักษาสถานะช่องทางการสื่อสารให้พร้อมใช้งานต่อเนื่อง และเปิดให้อุปกรณ์ที่มีเวอร์ชันโปรโตคอลต่างกันสื่อสารร่วมกันได้ตามช่วงที่รองรับ (ตอบสนอง UR-07, UR-09)
* **Verification Method:** Test (T) & Analysis (A) — ทดสอบจำลอง Handshake ระหว่างโหนดต่างเวอร์ชัน และทดสอบการเชื่อมต่อใหม่หลังตัดสัญญาณ
* **Description:** ระบบต้องเฝ้าระวังสถานะของช่องทางการสื่อสาร ตกลงเวอร์ชันโปรโตคอลระหว่างอุปกรณ์ และเชื่อมต่อใหม่โดยอัตโนมัติเมื่อเกิดข้อผิดพลาด
* **Input:** ข้อมูล `hello` handshake และสถานะการรับส่ง Heartbeat (Ping/Pong) บน WebSocket
* **Process:**
  1. *การตกลงเวอร์ชัน (Protocol Negotiation):* ในขั้นตอน Handshake ผ่านข้อความ `hello` และ `hello.ack`:
     - แต่ละโหนดระบุเวอร์ชันโปรโตคอลปัจจุบัน `v` และเวอร์ชันต่ำสุดที่รองรับ `min_v` (หรือ `min_supported_v`)
     - ตรวจสอบความเข้ากันได้: $\min(\text{local.v}, \text{remote.v}) \ge \max(\text{local.min\_v}, \text{remote.min\_v})$
     - หากเข้ากันได้ ให้ใช้เวอร์ชันที่ต่ำกว่าในคู่นั้นสำหรับการสื่อสาร
     - หากไม่มีช่วงเวอร์ชันที่รองรับร่วมกัน ให้ปิดการเชื่อมต่อ WebSocket ทันทีด้วย Close Code **4003** และส่ง Error Code **`E_UNSUPPORTED_VERSION`**
  2. *การตรวจสอบสถานะ (Liveness Monitoring):* ส่งแพ็กเก็ต Ping ทุก 15 วินาที หากไม่ได้รับ Pong ภายใน 45 วินาที ให้ถือว่าช่องทางสื่อสารขาดการเชื่อมต่อ (Authoritative Liveness ตัดสินแทน mDNS Stale)
  3. *การเชื่อมต่อใหม่ (Reconnection Backoff):* เมื่อการเชื่อมต่อขาด ให้เริ่มกลไก Reconnection แบบ Exponential Backoff (1, 2, 4, 8, 16, สูงสุด 30 วินาที พร้อม Jitter ±20%)
  4. *การจัดการคิว (Queue Catch-up):* พักข้อความคลิปบอร์ดที่เกิดขึ้นระหว่างออฟไลน์ไว้ใน Outbound Queue (สูงสุด 50 รายการ) เมื่อเชื่อมต่อสำเร็จ ส่งข้อมูลจาก Queue และดึงข้อมูลล่าสุดจาก Catch-up Queue มาอัปเดต
* **Output:** ช่องทางการสื่อสารคงสถานะออนไลน์ต่อเนื่อง ตกลงเวอร์ชันได้อย่างถูกต้อง และไม่มีปัญหา Socket ค้างสะสมในระบบ (No Socket Leak)

### FR-11: การจัดการอุปกรณ์และการเพิกถอนสิทธิ์ทั่วทั้งคลัสเตอร์ (Device Management & Signed Cluster Revocation)
* **Priority:** Must Have (MoSCoW)
* **Rationale:** เพื่อความมั่นคงปลอดภัยเมื่ออุปกรณ์ในคลัสเตอร์สูญหายหรือถูกขโมย โดยสามารถเพิกถอนสิทธิ์ได้ทันทีและมีผลทั่วทั้งคลัสเตอร์โดยที่เครื่องที่ถูกขโมยไม่สามารถชิงสั่งทำลายระบบได้ (ตอบสนอง UR-11)
* **Verification Method:** Test (T) & Inspection (I) — ทดสอบส่งคำสั่งเพิกถอน จับเวลาตัดการเชื่อมต่อ (< 2.0 วินาที) และตรวจสอบการปฏิเสธคำสั่ง Self-Revocation by Proxy
* **Description:** ระบบต้องอนุญาตให้ผู้ใช้ตรวจสอบรายการอุปกรณ์ และเพิกถอนสิทธิ์อุปกรณ์ที่ไม่ต้องการได้ทันที พร้อมกระจายคำสั่งเพิกถอนที่มีลายเซ็นดิจิทัลไปยังทุกอุปกรณ์ในคลัสเตอร์ และซิงก์สถานะกับอุปกรณ์ที่เคยออฟไลน์ผ่าน Anti-Entropy
* **Input:** คำสั่งเพิกถอนอุปกรณ์ (Revoke Command) จากหน้าต่างการตั้งค่า
* **Process:**
  1. แสดงรายการอุปกรณ์ที่เคยจับคู่ทั้งหมด พร้อมชื่อ ชนิด OS และสถานะออนไลน์/ออฟไลน์
  2. เมื่อผู้ใช้สั่งเพิกถอน:
     - เครื่องที่สั่งเพิกถอนลบ Key Fingerprint ออกจาก Trusted Store ในเครื่องตนเองทันที และตัดการเชื่อมต่อ Socket ภายใน **< 1.0 วินาที** (NFR-S05)
     - สร้าง `RevocationBroadcastToken` ที่ลงนามด้วย ECDSA P-256 Private Key ของตนเอง และบันทึกลง `revoked_tombstones.json` ถาวร
     - กระจายข้อความ `cluster.revocation` ไปยังทุก Peer ที่ออนไลน์ในวง LAN
  3. *มาตรการป้องกันการเพิกถอนโดยเครื่องที่ถูกขโมย (No Self-Revocation by Proxy):*
     - โหนดในคลัสเตอร์ที่ได้รับข้อความจะตรวจสอบลายเซ็นดิจิทัล แล้ว **Quarantine** เครื่องเป้าหมายทันที (ตัดการเชื่อมต่อและปฏิเสธ connection ใหม่ภายใน **< 2.0 วินาที** ทั่วทั้งเครือข่าย LAN) แต่จะลบออกจาก Trusted Store ถาวรก็ต่อเมื่อผู้ใช้ของเครื่องนั้นกดยืนยัน หากผู้ใช้ปฏิเสธ ระบบคืนสถานะให้เครื่องเป้าหมายและ quarantine ผู้สั่งแทน (PROTO §13.2)
     - **โหนดปลายทางจะไม่ยอมรับคำสั่งเพิกถอนตนเองที่ส่งมาจากโหนดอื่นเด็ดขาด** (หาก `revoked_id == my_id` จะไม่ประมวลผลคำสั่ง) เพื่อป้องกันไม่ให้เครื่องที่ถูกขโมยชิงส่งคำสั่งทำลายโหนดจริงในระบบ
     - แสดงการแจ้งเตือนระดับระบบ (Interactive System Notification) พร้อมปุ่ม "ยืนยันเพิกถอน" / "ปฏิเสธ" ทันทีเมื่อมีอุปกรณ์ในคลัสเตอร์ถูกสั่งเพิกถอน
  4. *การซิงก์สถานะกับอุปกรณ์ที่ออฟไลน์ (Handshake Anti-Entropy):*
     - ทุกโหนดแนบ `tombstones_hash` ไปในข้อความ `hello` / `hello.ack`
     - หากตรวจพบว่า Hash ไม่ตรงกัน ให้ส่งข้อความ `revocation.sync` เพื่อแลกเปลี่ยน Tombstones ที่ขาดไปทันที ป้องกันเครื่องที่ถูกเพิกถอนกลับมาเชื่อมต่อกับโหนดที่เคยออฟไลน์
* **Output:** อุปกรณ์ดังกล่าวถูกลบสถานะความเชื่อถือออกจากทุกอุปกรณ์ในคลัสเตอร์อย่างสมบูรณ์ และถูกปฏิเสธการเชื่อมต่อทุกรูปแบบในอนาคตด้วยรหัส `E_NOT_PAIRED`

### FR-12: การกำหนดค่าระบบและการเริ่มต้นอัตโนมัติ (System Configuration & Auto-Start Management)
* **Priority:** Should Have (MoSCoW)
* **Rationale:** มอบความต่อเนื่องในการทำงาน (Continuity) โดยโปรแกรมเริ่มทำงานพร้อมระบบปฏิบัติการในลักษณะเบื้องหลังโดยไม่รบกวนผู้ใช้ (ตอบสนอง UR-06, UR-07)
* **Verification Method:** Demonstration (D) & Inspection (I) — ตรวจสอบการลงทะเบียนในระบบปฏิบัติการ และทดสอบการรีบูตเครื่องเพื่อดูสถานะเริ่มต้นใน System Tray
* **Description:** ระบบต้องบันทึกการตั้งค่าของผู้ใช้ และสามารถลงทะเบียนเพื่อเริ่มต้นทำงานพร้อมระบบปฏิบัติการได้
* **Input:** ค่าการตั้งค่าจากผู้ใช้ (การรับไฟล์อัตโนมัติ, โฟลเดอร์ปลายทาง, ค่า TTL, การเปิด-ปิดระบบ)
* **Process:**
  1. บันทึกการกำหนดค่าลงไฟล์ JSON ในเครื่องและนำไปประยุกต์ใช้ทันทีโดยไม่ต้องรีสตาร์ตแอปพลิเคชัน
  2. เมื่อเปิดตัวเลือก Auto-Start:
     - macOS: บน macOS 13+ ลงทะเบียนผ่าน Service Management Framework (`SMAppService`) และบน macOS 12 ใช้การลงทะเบียน `LaunchAgent` `.plist`
     - Windows: ลงทะเบียนคีย์ใน Windows Registry (`Software\Microsoft\Windows\CurrentVersion\Run`)
  3. เมื่อระบบบูตขึ้นมา แอปพลิเคชันต้องเปิดทำงานในสถานะย่อตัวลง System Tray / Menubar ทันที โดยไม่เปิดหน้าต่างโปรแกรมรบกวนผู้ใช้
* **Output:** ระบบทำงานสอดคล้องกับการตั้งค่า และเริ่มต้นทำงานพร้อมระบบปฏิบัติการอย่างราบรื่น

## 3.3 ความต้องการที่ไม่ใช่ด้านหน้าที่ (Non-Functional Requirements: NFR)
*ทุกข้อกำหนดต้องสามารถวัดผลและตรวจสอบได้เชิงปริมาณ (Measurable & Verifiable)*

### 3.3.1 ด้านประสิทธิภาพและความหน่วง (Performance Matrix by Capability Tier)

| รหัส | ตัวชี้วัด | ขอบเขตแพลตฟอร์ม | ค่าเป้าหมาย (Target) | วิธีการวัดผลและการตรวจสอบ |
|---|---|---|---|---|
| **NFR-P01A** | ความหน่วงคลิปบอร์ดข้อความ (Tier 1: Full Passive) | macOS ↔ Windows | **p50 < 300 ms**<br>**p95 < 1,000 ms** | จับเวลาตั้งแต่กด Ctrl+C / Cmd+C บนเครื่องต้นทาง จนกระทั่งข้อมูลถูกเขียนลงคลิปบอร์ดปลายทางและพร้อมกดวาง ทำการทดสอบจำนวน 100 รอบ |
| **NFR-P01B** | ความหน่วงคลิปบอร์ดขาเข้า (Tier 2: Inbound Passive) | Desktop → Android | **p95 < 1,200 ms** | จับเวลาตั้งแต่กดคัดลอกบน Desktop จนกระทั่ง `ClipboardManager` บน Android บันทึกข้อมูลสำเร็จ |
| **NFR-P01C** | เวลาในการตอบสนองคำสั่ง (Tier 2: Outbound Assisted) | Android → Desktop | **< 800 ms** | จับเวลาตั้งแต่แตะ Quick Settings Tile จนข้อความปรากฏบนคลิปบอร์ดของ Desktop ปลายทาง |
| **NFR-P01D** | เวลาในการส่งผ่านส่วนขยาย (Tier 3: Manual-Assist) | iOS → Desktop | **< 1,500 ms** | จับเวลาตั้งแต่กดปุ่มส่งใน Share Extension จนกระทั่งข้อมูลถูกประมวลผลเสร็จสิ้นบน Desktop |
| **NFR-R03A** | การใช้พลังงานเบื้องหลัง (Tier 2: Android Service) | Android (Foreground Service) | **< 3% ต่อ 24 ชม.** | ตรวจวัดด้วย Android Battery Historian ในสภาวะเชื่อมต่อ Wi-Fi ต่อเนื่องตลอด 24 ชั่วโมง |
| **NFR-R03B** | การใช้ทรัพยากรหน่วยความจำของส่วนขยาย (Tier 3: iOS) | iOS (Share Extension) | **Peak RAM < 30 MB** | ตรวจวัดด้วย Xcode Memory Report / Instruments ระหว่างการส่งข้อมูลผ่าน Share Extension เพื่อป้องกันไม่ให้ถูก OS ปิดการทำงาน (Jetsam Kill) |

#### ตัวชี้วัดด้านประสิทธิภาพเพิ่มเติม (Additional Performance Requirements)
* **NFR-P02 (ความหน่วงการซิงก์คลิปบอร์ดรูปภาพ):** การซิงก์ภาพขนาด 2 MB ต้องสำเร็จภายในเวลา **p95 < 2,500 ms**
* **NFR-P03 (ความเร็วในการถ่ายโอนไฟล์):** อัตรา Throughput ในการถ่ายโอนไฟล์ขนาดใหญ่ (ทดสอบที่ 4 GB บน Mobile และ 10 GB บน Desktop) ต้องทำได้ **≥ 60% ของค่า Throughput สูงสุดที่วัดได้จาก iperf3 baseline** ภายใต้สภาพแวดล้อม Test Rig มาตรฐาน: เราเตอร์ Wi-Fi 6 (802.11ax) ย่านความถี่ 5 GHz, Channel Width 80 MHz, ค่าความแรงสัญญาณ RSSI ≥ -60 dBm หรือสายเคเบิล 1 Gbps Ethernet LAN
* **NFR-P04 (เวลาในการค้นพบอุปกรณ์):** ระบบต้องค้นพบอุปกรณ์อื่นในเครือข่ายเดียวกันภายในเวลา **< 3 วินาที** นับจากเปิดโปรแกรม
* **NFR-P05 (เวลาในการประมวลผลแปลงภาพ):** การแปลงโครงสร้างภาพความละเอียด 4K ระหว่าง OS ต้องใช้เวลา **< 200 ms** โดยกำหนดให้ระบบเรียกใช้ Native Platform Image Codec (macOS/iOS `CoreGraphics` & `ImageIO`, Windows `WIC`, Android `BitmapFactory`) เพื่อใช้ Hardware Acceleration แทนการ Decode บน CPU ของ Dart VM ล้วน — ค่า 200 ms เป็นเป้าหมายเบื้องต้นที่ต้องยืนยันด้วย benchmark บนเครื่องอ้างอิงใน T1.8 (p95 จาก 50 ครั้ง) และปรับตามผลวัดผ่าน change request

### 3.3.2 ด้านการใช้ทรัพยากรระบบ (Resource Utilization Requirements)
* **NFR-R01 (การควบคุมหน่วยความจำขณะส่งไฟล์และการทดสอบ Soak Test):** ขณะสตรีมไฟล์ขนาดใหญ่ (10 GB บน Desktop และ 4 GB บน Mobile) อัตราการเพิ่มของหน่วยความจำ (Delta RSS) ต้อง **ไม่เกิน 50 MB เหนือ Baseline ปกติ** ตลอดระยะเวลาการส่ง (ไม่กำหนด Peak RSS แบบค่าสัมบูรณ์บน Desktop เพราะ baseline ของ Flutter ขึ้นกับแพลตฟอร์ม — วัด baseline จริงใน T4.1 ก่อน; ส่วน iOS Share Extension กำหนด Peak RAM < 30 MB เพื่อป้องกัน Jetsam Kill) และในการทดสอบความคงทนระยะยาว 72 ชั่วโมง (72-hour Soak Test) อัตราการเพิ่มของหน่วยความจำ RSS ต้อง **≤ 5%** หลังจากผ่านพ้นช่วง Warm-up 30 นาทีแรก
* **NFR-R02 (การใช้ CPU ในสถานะไม่ได้ใช้งาน):** บน Desktop เมื่อไม่มีการรับส่งข้อมูล อัตราการใช้ CPU เฉลี่ยต้อง **< 0.5%** ตลอดระยะเวลา 8 ชั่วโมง (โดยบน Windows ที่ทำงานแบบ Event-Driven Clipboard Listener ต้องทำได้เฉลี่ย **< 0.2%**)
* *(หมายเหตุ: ข้อกำหนด NFR-R03A และ NFR-R03B ได้รับการระบุไว้ในตาราง Matrix หัวข้อ 3.3.1)*

### 3.3.3 ด้านความน่าเชื่อถือและความสมบูรณ์ของข้อมูล (Reliability Requirements)
* **NFR-RE01 (ความสมบูรณ์ของไฟล์):** ไฟล์ที่ถ่ายโอนสำเร็จทุกไฟล์ต้องมีค่า SHA-256 Checksum ตรงกับต้นฉบับ **100% จากการทดสอบส่งไฟล์จำนวน 500 ครั้ง**
* **NFR-RE02 (การระงับเหตุการณ์วนซ้ำและการลู่เข้าของข้อมูล):** ในการทดสอบกระจายข้อมูลคลิปบอร์ด 1,000 เหตุการณ์พร้อมกันบน 4 อุปกรณ์ ระบบรับประกัน Eventual Consistency และข้อมูลลู่เข้าสู่สถานะเดียวกัน (Convergence) ตามลำดับ HLC Last-Writer-Wins (LWW) โดย **ไม่มีการเกิด Infinite Feedback Loop และไม่มีการสูญหายของข้อมูลที่ถูกต้องตามลำดับเวลา**
* **NFR-RE03 (การกู้คืนการเชื่อมต่อ):** เมื่อจำลองการตัดและต่อสายสัญญาณเครือข่ายจำนวน 20 ครั้ง ระบบต้องสามารถเชื่อมต่อใหม่สำเร็จ 100% โดย **ไม่เกิดปัญหา Socket ค้างสะสม (Zero Socket Leak)**

### 3.3.4 ด้านความปลอดภัยและความเป็นส่วนตัว (Security Requirements)
* **NFR-S01 (การเข้ารหัสข้อมูล):** การสื่อสารทุกช่องทาง (Control & Data Plane) ต้องใช้โปรโตคอล **TLS 1.3 ล้วน** (บังคับใช้ Cipher Suite สมัยใหม่ เช่น `TLS_AES_128_GCM_SHA256`) และปฏิเสธการลดระดับโปรโตคอล (Downgrade Attack) ทั้งหมด
* **NFR-S02 (การจัดเก็บกุญแจความปลอดภัย):** Private Key ของอุปกรณ์ต้องถูกเข้ารหัสด้วย Secure Storage ประจำ OS (Keychain, DPAPI, key ที่อยู่ใน Android Keystore) แบบ envelope encryption (PROTO §4.2 — key ไม่ใช่ hardware-bound เพราะ Dart TLS ต้องได้ key เป็น bytes) และ **ต้องไม่ปรากฏเป็นไฟล์ข้อความธรรมดา (Plaintext) บนดิสก์เด็ดขาด**
* **NFR-S03 (การป้องกันการเขียนไฟล์อันตราย):** ระบบต้องสามารถป้องกันการโจมตีประเภท Path Traversal, Directory Traversal (`../`), Null Byte Injection, และ Windows Reserved Filenames ได้ **100% จากชุดทดสอบการโจมตี 12 รูปแบบ**
* **NFR-S04 (การกรองข้อมูลอ่อนไหว):** ระบบต้องกรองและระงับการส่งออกข้อมูลคลิปบอร์ดที่มี **Known OS Sensitive Marker ที่รู้จักได้ 100% ครบทั้ง 5 รูปแบบ** ประกอบด้วย:
  1. macOS: `org.nspasteboard.ConcealedType`
  2. macOS: `org.nspasteboard.TransientType` / `com.agilebits.onepassword`
  3. Windows: `ExcludeClipboardContentFromMonitorProcessing`
  4. Windows: `CanIncludeInClipboardHistory` หรือ `CanUploadToCloudClipboard` (เมื่อมีค่าเป็น 0 / FALSE)
  5. Android: `ClipDescription.EXTRA_IS_SENSITIVE` / `Clipboard.EXTRA_IS_SENSITIVE`
  จากการทดสอบคัดลอก 100 ครั้ง จาก Password Managers (1Password, Bitwarden, KeePass, Apple Keychain)
* **NFR-S05 (เวลาในการบังคับใช้การเพิกถอน):** เมื่อกดเพิกถอนอุปกรณ์ ระบบต้องทำการตัดการเชื่อมต่อและเพิกถอนสิทธิ์บนเครื่องที่สั่ง **ภายในเวลา < 1.0 วินาที** และโหนดที่ออนไลน์ทั้งหมดในคลัสเตอร์ LAN ต้องดำเนินการเพิกถอนเสร็จสิ้น **ภายในเวลา < 2.0 วินาที**

### 3.3.5 ด้านความง่ายในการใช้งานและการเข้าถึง (Usability Requirements)
* **NFR-U01 (การลดขั้นตอนการทำงาน):** ระบบต้องช่วยลดขั้นตอนการโต้ตอบของผู้ใช้ (Interaction Count) ลง **≥ 70%** เมื่อเทียบกับวิธีการส่งข้อมูลเดิมใน 5 สถานการณ์ทดสอบ
* **NFR-U02 (คะแนนความพึงพอใจการใช้งาน):** ซอฟต์แวร์ต้องได้รับคะแนนประเมินความง่ายในการใช้งานมาตรฐาน **System Usability Scale (SUS) ≥ 75 คะแนน** จากกลุ่มผู้ทดสอบจริง
* **NFR-U03 (การทำงานอย่างเงียบสงบ):** เมื่อเปิดเครื่องใหม่ โปรแกรมต้องซ่อนตัวลง System Tray / Menubar โดย **ไม่อนุญาตให้แสดง Pop-up หรือหน้าต่างหลักรบกวนสายตาผู้ใช้**

### 3.3.6 ด้านคุณภาพเชิงวิศวกรรม ความสามารถในการบำรุงรักษา และการเข้าถึง (Engineering Quality, Maintainability, Localization & Accessibility)
* **NFR-M01 (คุณภาพซอฟต์แวร์และการทดสอบ):** โค้ดใน Monorepo ต้องมี Unit/Integration Test ครอบคลุม **≥ 75% Code Coverage**, ผ่านการตรวจสอบ `melos run analyze` โดยมีข้อผิดพลาดหรือ Warning เป็น 0, และปฏิบัติตามกฎ PR ขนาดเล็ก $\le 400$ บรรทัด
* **NFR-L01 (การรองรับภาษา):** ส่วนติดต่อผู้ใช้ (UI) ต้องรองรับทั้งภาษาไทยและภาษาอังกฤษ โดยสามารถสลับภาษาได้จากการตั้งค่าของแอปพลิเคชัน
* **NFR-A01 (การเข้าถึงสำหรับทุกคน):** ส่วนติดต่อผู้ใช้บน Desktop ต้องรองรับการนำทางด้วยแป้นพิมพ์อย่างสมบูรณ์ (Full Keyboard Navigation ผ่าน Tab / Enter / Esc) และมีค่า Contrast Ratio ของข้อความ $\ge 4.5:1$ ตามมาตรฐาน WCAG 2.1 Level AA

## 3.4 ความต้องการด้านส่วนต่อประสานภายนอก (External Interface Requirements)

### 3.4.1 ส่วนต่อประสานผู้ใช้ (User Interfaces: UI)
* **UI-01 (Desktop Menubar / System Tray):** เมนูถาวรบนแถบงานของ Desktop แสดงสถานะการเชื่อมต่อ รายชื่ออุปกรณ์ออนไลน์ เมนูเปิด Dropzone และเมนูเข้าสู่หน้าตั้งค่า
* **UI-02 (Desktop Floating Dropzone):** หน้าต่างลากวางไฟล์ขนาดเล็กที่สามารถเปิดขึ้นมาได้อย่างรวดเร็ว รองรับการลากไฟล์มาวางแล้วเลือกส่งไปยังอุปกรณ์ปลายทาง
* **UI-03 (Pairing & SAS Verification Dialog):** หน้าจอแสดงภาพ QR Code สำหรับการจับคู่ พร้อมหน้าต่างแสดงรหัสตัวเลข 6 หลักขนาดใหญ่ที่ชัดเจนสำหรับยืนยันความถูกต้อง
* **UI-04 (File Transfer Progress Indicator):** แถบแสดงความคืบหน้าการส่งไฟล์ แสดงเปอร์เซ็นต์ ความเร็วในการส่ง (MB/s) และเวลาที่เหลือโดยประมาณ
* **UI-05 (Mobile Quick Settings Tile & Share Target):** ปุ่มทางลัดบนแผงควบคุมด่วนของ Android และส่วนขยายบน System Share Sheet ของ iOS และ Android เพื่อการกดส่งข้อมูลได้จากทุกแอป

### 3.4.2 ส่วนต่อประสานด้านฮาร์ดแวร์ (Hardware Interfaces)
* **HW-01 (Network Interface):** ต้องรองรับการทำงานผ่านการ์ดเชื่อมต่อเครือข่าย Wi-Fi (802.11n/ac/ax) และ Ethernet (RJ-45) ที่รองรับการกระจายสัญญาณแพ็กเก็ต Multicast
* **HW-02 (Camera Interface):** เชื่อมต่อกับกล้องถ่ายภาพบนอุปกรณ์พกพาสำหรับอ่านและถอดรหัสภาพ QR Code ในขั้นตอนจับคู่อุปกรณ์

### 3.4.3 ส่วนต่อประสานด้านซอฟต์แวร์ (Software Interfaces)
* **SW-01 (OS Clipboard APIs):** เชื่อมต่อกับ `NSPasteboard` (macOS), Win32 Clipboard API (Windows), และ `ClipboardManager` (Android)
* **SW-02 (Secure Storage APIs):** เชื่อมต่อกับ Apple Keychain Services (macOS/iOS), Data Protection API / DPAPI (Windows), และ Android Keystore System (Android)
* **SW-03 (Media Storage APIs):** เชื่อมต่อกับ Android `MediaStore` และ Apple `PhotoKit` เพื่อจัดเก็บรูปภาพและวิดีโอที่ได้รับเข้าสู่คลังภาพของเครื่องโดยตรง

### 3.4.4 ส่วนต่อประสานด้านการสื่อสาร (Communication Interfaces)
* **CI-01 (mDNS/DNS-SD):** สื่อสารผ่านโปรโตคอล UDP พอร์ต 5353 มาตรฐาน RFC 6762 / 6763 สำหรับค้นหาโหนดในวง LAN
* **CI-02 (Control Plane WebSocket):** สื่อสารผ่าน WebSocket over TLS 1.3 บนช่วงพอร์ต TCP 53317–53417 สำหรับส่งข้อมูลการควบคุมและคลิปบอร์ด พร้อมการเจรจาเวอร์ชันโปรโตคอล (Negotiate $\min \ge \max$ หรือปิดด้วย Close Code 4003 `E_UNSUPPORTED_VERSION`)
* **CI-03 (Data Plane HTTP):** สื่อสารผ่าน HTTP/1.1 Chunked Transfer over TLS 1.3 บนช่วงพอร์ต TCP เดียวกันสำหรับสตรีมไฟล์ขนาดใหญ่

## 3.5 สภาพแวดล้อมการทำงานของระบบ (System Environment)

### 3.5.1 สภาพแวดล้อมฝั่งผู้ใช้งาน (Target Execution Environment)
* **macOS:** macOS 12.0 (Monterey) ขึ้นไป จนถึง macOS 15 (Sequoia) | รองรับสถาปัตยกรรม Apple Silicon (M1/M2/M3/M4) และ Intel x86_64 | RAM ขั้นต่ำ 4 GB | เนื้อที่ว่าง 150 MB
* **Windows:** Windows 10 (Build 19041) หรือ Windows 11 (รวม 23H2/24H2) | รองรับสถาปัตยกรรม x64 และ ARM64 | RAM ขั้นต่ำ 4 GB | เนื้อที่ว่าง 150 MB
* **Android:** Android 10 (API Level 29) ขึ้นไป จนถึง Android 15 | สถาปัตยกรรม ARM64-v8a | RAM ขั้นต่ำ 3 GB | เนื้อที่ว่าง 80 MB
* **iOS:** iOS 15.0 ขึ้นไป จนถึง iOS 18 | อุปกรณ์ iPhone และ iPad (สถาปัตยกรรม ARM64) | เนื้อที่ว่าง 80 MB

### 3.5.2 สภาพแวดล้อมด้านเครือข่าย (Network Environment)
* ทำงานบนโครงข่ายเครือข่ายท้องถิ่น (Local Area Network - LAN / Wi-Fi เดียวกัน) วง Subnet เดียวกัน
* เราเตอร์เครือข่ายต้องอนุญาตการส่งข้อมูลแบบ Multicast (UDP พอร์ต 5353) และเปิดให้สื่อสารระหว่างเครื่องผ่านพอร์ต TCP 53317–53417
* เครือข่ายต้องไม่มีการเปิดใช้งานฟีเจอร์ AP Isolation หรือ Client Isolation
* **ระบบสามารถทำงานแบบ Standalone ได้สมบูรณ์ 100% โดยไม่ต้องเชื่อมต่อสัญญาณอินเทอร์เน็ตภายนอก**

### 3.5.3 สภาพแวดล้อมการพัฒนาและทดสอบ (Development & Test Stack)
* **ภาษาและเฟรมเวิร์กหลัก:** Dart (Flutter Framework) สำหรับแกนการทำงานข้ามแพลตฟอร์ม
* **ภาษา Native เฉพาะแพลตฟอร์ม:** Swift (macOS/iOS), C++ (Windows), Kotlin (Android) สำหรับเข้าถึงระบบคลิปบอร์ดระดับต่ำ
* **การทดสอบประสิทธิภาพ:** ใช้เครื่องมือ `iperf3` เพื่อสร้าง Baseline อัตราความเร็วเครือข่าย, ใช้ Activity Monitor / Windows Performance Monitor และ Android Battery Historian ตรวจวัดการกินพลังงาน

*คำอธิบายสัญลักษณ์วิธีการตรวจสอบ (Verification Methods):*
- **T (Test):** ทดสอบด้วยระบบทดสอบอัตโนมัติ (Automated Unit, Integration หรือ Regression Test)
- **I (Inspection):** ตรวจสอบเชิงประจักษ์จากซอร์สโค้ด, การตั้งค่า, เอกสาร, หรือการตรวจจับ Network Packet
- **A (Analysis):** การวิเคราะห์เชิงตรรกะ แบบจำลองทางคณิตศาสตร์ หรือการคำนวณเปรียบเทียบ
- **D (Demonstration):** การสาธิตการทำงานจริงของระบบต่อหน้าผู้ประเมินตามสถานการณ์ทดสอบมาตรฐาน
